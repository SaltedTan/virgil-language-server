# Manual testing

In CI, the automated editor tests run the plain Neovim configuration and VS Code on Linux and macOS. A scripted test runs the LazyVim configuration, in CI on Linux, on Linux and macOS in a weekly workflow and in the release workflow, and locally. Those two workflows also run the VS Code test through Remote-SSH on Linux. Local runs are recorded under [Results](#results). This page lists what they cover, the editor and platform combinations for optional manual checks, how to check each feature, and the results for each release. A release needs automated evidence only: the [release workflow](releasing.md#how-the-workflow-works) runs the editor tests on the release's own archives and VSIX and publishes only if they pass, and the [editor evidence contract](../test/e2e/RESULTS.md#the-release-gate) defines what counts as evidence. Manual checks are optional.

## What the automated tests cover

The headless Neovim, Extension Host, and scripted LazyVim tests use the same fixture, [`test/e2e/nvim/fixture`](../test/e2e/nvim/fixture/), copied into a temporary directory.

The VS Code and plain Neovim suites check exact document highlight ranges and Read, Write, and Text kinds in the fixture. The LazyVim suite waits for snacks.nvim words to hold the symbol's highlights, then checks next and previous navigation through `]]` and `[[`.

All three editor suites check inferred type and parameter-name inlay hints at exact UTF-16 positions after non-ASCII text, through `vscode.executeInlayHintProvider` and `vim.lsp.inlay_hint.get()`; LazyVim also checks that hints are enabled by default.

All three editor suites also check that type definition on the `puts` call goes to the exact `StringBuilder` class name in the library and that the `int` local has no type location. VS Code calls `vscode.executeTypeDefinitionProvider`; plain Neovim drives `vim.lsp.buf.type_definition()`, and LazyVim drives `gy` and checks its destination.

They also check that implementation in `words/Shapes.v3` returns the exact names of the subclasses of `Shape`, direct and transitive, and of the methods that override its `area`, and nothing for the unextended `Circle`. VS Code calls `vscode.executeImplementationProvider`. Plain Neovim drives `vim.lsp.buf.implementation()` and LazyVim drives `gI`, and both check the jump from `Polygon` to its one subclass, `Square`.

VS Code and plain Neovim also check type hierarchy there: the exact item of `Polygon`, with its declaration's range and detail, its one supertype, `Shape`, its one subtype, `Square`, and `Shape`'s subtypes, `Polygon` and `Circle`. VS Code calls `vscode.prepareTypeHierarchy`, `vscode.provideSupertypes`, and `vscode.provideSubtypes`; plain Neovim makes the same requests, also checking each item's data, and checks the quickfix list that `vim.lsp.buf.typehierarchy("subtypes")` fills. LazyVim binds no key to type hierarchy, so its suite doesn't check it.

They also check call hierarchy in `words/Calls.v3`: the exact item of `square`, prepared from one of its calls, its two callers, `sumSquares`, with the ranges of its two calls, and `cube`, and the one function that `sumSquares` calls, `square`. VS Code calls `vscode.prepareCallHierarchy`, `vscode.provideIncomingCalls`, and `vscode.provideOutgoingCalls`; plain Neovim makes the same requests, also checking each item's data, and checks the quickfix list that `vim.lsp.buf.incoming_calls()` fills. The LazyVim suite doesn't check the `gai` and `gao` pickers.

The [clean install test](releasing.md#clean-install-test) additionally follows the README installation commands with release assets; its separate fixture, coverage, prerequisites, and artifacts are documented there.

The editor tests don't cover:

- VS Code Remote-WSL. Nothing runs inside WSL 2.
- VS Code Remote-SSH from a Mac, or to another machine. The Remote-SSH test connects a Linux client to the same machine. See the [VS Code procedure](#vs-code) for its recovery checks and remaining gaps.
- An installed VSIX on macOS on every pull request. CI runs the Extension Host test there only on the extension from source; the weekly editor tests and the release workflow run it on an installed VSIX, including the release dry run of a pull request that changes the release path or the editor tests.
- In plain Neovim, configuration changes other than an unsaved edit to the project file: changes on disk and a missing Virgil root. The Extension Host test covers them in VS Code, with changed settings, and the LazyVim test covers them in LazyVim.
- Restarting the server from plain Neovim. The LazyVim test restarts it with `:LspRestart`, or `:lsp restart` on Neovim 0.12.
- What the editor shows. The tests read diagnostics, symbols, locations, hover text, signature help, and completion items through editor APIs, not from the Problems view, the outline, a hover popup, a signature popup, a completion menu, or a notification. The LazyVim test reads the text of noice.nvim's hover and signature windows and blink.cmp's menu items, but not how they look.

[Editor test results](../test/e2e/RESULTS.md) gives each automated check a stable ID, maps the checks to the matrix below and the VS Code checklist, and lists what no test covers.

## Procedure

### Before you start

1. Use the release candidate: the archives and VSIX from a [dry run](releasing.md#dry-runs) of the release preparation branch, or from the published prerelease. For VS Code, install the matching [platform VSIX](../clients/vscode/README.md#installing-from-a-vsix) on the machine that holds the files. For Neovim or LazyVim, [install the server archive](releasing.md#installing) there, then the editor configuration.
2. On the same machine, clone the repository at the same commit, with submodules; for WSL 2, clone inside WSL, so that files keep LF line endings. Its `vendor/virgil` is a Virgil checkout at the server's Virgil revision: use it as the Virgil root.
3. Copy the fixture, so that edits don't touch the checkout: `cp -R test/e2e/nvim/fixture /tmp/virgil-check`. Its `bad.v3` has a syntax error on line 3. Its project file defines a project `words`, which uses Virgil's `lib/util`.
4. Record the server's version (from the VS Code output channel for a bundled install, or `virgil-lsp --version` for an external install), the editor's version, the extension's version, and the platform.

### VS Code

Follow the [manual checklist](../clients/vscode/README.md#manual-checklist), which covers local Linux, Remote-SSH, Remote-WSL, and macOS. Its steps check the features as follows: diagnostics in steps 3, 4, 6, and 7; document symbols in step 5; definition, hover, signature help, references, document highlights, and workspace symbols in step 7; rename in step 8; completion in step 9; configuration changes in steps 10 to 12; and restart in step 13. Steps 1, 2, and 14 to 17 check startup, startup errors, the message trace, and recovery.

The [Extension Host suite](../clients/vscode/README.md#extension-host-test) also checks lost framing in two runs: with the server paused and a hover or rename preparation request sent, a script writes a line that isn't a message, then the server resumes. Both runs check that the client reports the fault and stops; the rename must also fail with a connection read error within one second of the test asking for the line, before the two-second shutdown timeout. Both checks run through Remote-SSH too.

For VS Code Remote-SSH, each release needs a passing automated run instead of a manual session: the [Remote-SSH test](../clients/vscode/README.md#remote-ssh-test), with official VS Code and Microsoft's Remote-SSH extension, from a Linux client, against the release's own VSIX and Linux server. The release workflow runs it in the dry run of the release branch and in the tag's run, and publishes only if it passes ([Making a release](releasing.md#making-a-release)). Of checklist step 17, it checks a restart and a configuration change during a server's recovery, a write to a dead server, and the crash limit, but not closing the window during the recovery; that, and what VS Code shows, are gaps that the [coverage contract](../test/e2e/RESULTS.md#coverage-of-the-matrix-and-the-checklist) lists. The test's [coverage and limitations](../clients/vscode/README.md#remote-ssh-test) explain why. A check from a Mac client is deferred ([#186](https://github.com/SaltedTan/virgil-language-server/issues/186)) and no release requires it. Record any optional manual observations under [Results](#results).

### Neovim and LazyVim

Set `VIRGIL_LOC` to the checkout's `vendor/virgil`, change to `/tmp/virgil-check`, and start Neovim there. Neovim 0.11 doesn't show diagnostics as virtual text by default; `:lua vim.diagnostic.setloclist()` lists them.

For LazyVim on Linux and macOS, run `test/e2e/lazyvim/run.sh --archive <archive>` from the checkout. The release workflow's dry run already runs it on the release's archives, on Linux with Neovim 0.11.6 and 0.12.6 and on macOS ([CI](../test/e2e/lazyvim/README.md#ci)); a local run adds your Neovim and machine. It uses Neovim on `PATH`, an isolated starter and plugins, and LazyVim's own keys to run the checks described in the [LazyVim test](../test/e2e/lazyvim/README.md). Record its summary, and look through the steps by hand for what it doesn't check.

1. **Diagnostics.** Open `bad.v3`. It has one error, "invalid start of expression", at line 3, column 27. Without saving, replace line 3 with `component C { def value = 1; }`; the error disappears. Undo the edit; it comes back. Open `words/Words.v3`. After a moment, it has one error, "expected int in var initialization, got Array<byte>", on line 7.
2. **Document symbols.** In `words/Words.v3`, `gO` (or `:lua vim.lsp.buf.document_symbol()`) lists the component `Words` and its method `join`.
3. **Definition.** On `StringBuilder` in line 7, `CTRL-]` (`gd` in LazyVim, or `:lua vim.lsp.buf.definition()`) opens Virgil's `lib/util/StringBuilder.v3` at `class StringBuilder`, on line 19. On the `puts` call, `:lua vim.lsp.buf.type_definition()` (`gy` in LazyVim) goes to that same class; on the `int` local `line`, it has no destination. In `words/Shapes.v3`, `:lua vim.lsp.buf.implementation()` (`gI` in LazyVim) on `Polygon`, in line 8, goes to its one subclass, `Square`, in line 11; on `Shape`, in line 5, it lists `Polygon`, `Square`, and `Circle`.
4. **Hover.** On the same `StringBuilder`, `K` shows `class StringBuilder`.
5. **Signature help.** In `words/Words.v3`, put the cursor just after the `(` of `.puts(a)` in line 7 and, in Insert mode, press `CTRL-S` (Neovim 0.11's default mapping; in LazyVim, `CTRL-S` saves the file, so press `CTRL-K`), or run `:lua vim.lsp.buf.signature_help()` (`gK` in LazyVim) from Normal mode. A window shows `def puts(s: Array<byte>) -> this`, with `s: Array<byte>` highlighted. Just past the `)`, it shows nothing. Plain Neovim doesn't open the window as you type `(` or `,` without a plugin or an `LspAttach` autocommand that calls it; LazyVim's noice.nvim does ([Signature help](architecture.md#signature-help)).
6. **References.** Return to `words/Words.v3`, since the library file that step 3 opened belongs to another server without the fixture's project. On `StringBuilder` in line 7, run `:lua vim.lsp.buf.references()`. The list includes this use, the class's name in `lib/util/StringBuilder.v3`, and its uses in the other `lib/util` files that the fixture's project includes ([References](architecture.md#references)).
7. **Workspace symbols.** Back in `words/Words.v3`, run `:lua vim.lsp.buf.workspace_symbol("join")`. The list shows the method `join` in `words/Words.v3`, on line 6, although nothing uses it ([Workspace symbols](architecture.md#workspace-symbols)).
8. **Rename.** In `words/Words.v3`, with the cursor on `line` in line 7, run `:lua vim.lsp.buf.rename("text")` (in LazyVim, press `<leader>cr`, and enter `text` when it asks for the new name). Neovim shows the server's reason, "the project's analysis has errors; rename needs a program that verifies". Without saving, change line 7 to `var line = StringBuilder.new().puts(a).putc(' ').puts(b).toString();` and line 8 to `return line.length;`, and run it again: both uses become `text`. `u` makes them `line` again, and `u` once more brings back the type error ([Rename](architecture.md#rename)).
9. **Completion.** In `words/Words.v3`, press `o` on line 7 to open a line below it. In plain Neovim, press `CTRL-X CTRL-O`: after a moment, the menu lists the names in scope first, `line`, `a`, `b`, `this`, and `join`, then the library's types and the builtin types, and last the keywords that start a statement, from `break` to `while`. Press `CTRL-E` to close it, type `whi`, and press `CTRL-X CTRL-O` again: the menu lists only `while`, which `CTRL-Y` accepts. In LazyVim, the menu appears as you type `w` with no key and narrows as you type `whi`; `Enter` accepts `while`. blink.cmp, LazyVim's completion plugin, adds words from the buffer only where the server offers nothing, as in a comment. The line reads `while`. Press `Esc` and `u`: the line is gone and the buffer is unmodified. In LazyVim, the first `u` brings back `whi` and a second removes the line, here and below. Open the line again and complete `li` the same way: `line` comes first, as a variable with `var line: int`, and accepting it makes the line read `line`; `Esc` and `u` remove the line again. Open the line again, type `a.`, and complete the same way (LazyVim shows the menu as you type the `.`): it lists only `length`, a field with `def length: int`, since `a` is a string (LazyVim's menu lists its snippets after it), and accepting it makes the line read `a.length`; `Esc` and `u` remove the line again. Inside the comment on line 3, `CTRL-X CTRL-O` (or typing a word or a `.` in LazyVim) offers nothing from the server ([Completion](architecture.md#completion), [Member completion](architecture.md#member-completion), [the Neovim configuration](../editors/nvim/README.md#completion)).
10. **Configuration changes.** Edit the project file on disk first, before it has been open in Neovim: opening or closing it in a buffer makes the server read it again, which would hide whether the server noticed the change by itself. Once `words/Words.v3` has its type error on line 7 again, add `"bogus": 1,` after the opening brace of `.virgil-lsp.json` from a terminal. `:lua vim.diagnostic.setqflist()` lists the diagnostics of every file, open or not. Whether an `UnknownField` error from `virgil-lsp` appears there at once depends on whether Neovim declares file watching, which `:lua =vim.lsp.protocol.make_client_capabilities().workspace.didChangeWatchedFiles` shows ([Changes on disk](../editors/nvim/README.md#changes-on-disk)). On macOS, Neovim 0.11 declares it, the server registers its watchers, and the error appears without further action. On Linux and in WSL 2, it doesn't: the error doesn't appear within a few seconds, and appears when a `.v3` buffer is next opened, changed, or saved. Remove the line on disk again, and undo any change to a `.v3` buffer; the error disappears. Then open `.virgil-lsp.json` and, without saving, add the same line: the error appears on that line. Undo the edit; the error disappears. Then quit, start Neovim with `VIRGIL_LOC` unset, and open `.virgil-lsp.json`: Neovim shows the warning "Invalid project file …" (LazyVim doesn't, unless noice's LSP message handler is turned off; see [LazyVim](../editors/nvim/README.md#lazyvim)), and the file has a `MissingVirgilRoot` error on the `virgilDependencies` line. Quit again.
11. **Restart.** Start Neovim with `VIRGIL_LOC` set again, open `words/Words.v3`, and wait for its type error on line 7. In LazyVim, run `:LspRestart`, or `:lsp restart` on Neovim 0.12 and later, where nvim-lspconfig no longer defines `:LspRestart`. In plain Neovim, run `:lua vim.lsp.stop_client(vim.lsp.get_clients({ name = "virgil_lsp" }))`, then `:edit`. A new server attaches, and `words/Words.v3` gets its error again. If the old server exited with a nonzero status, Neovim warns "Client virgil_lsp quit with exit code …".

### Collecting logs

- **VS Code:** the "Virgil Language Server" output channel holds the extension's startup messages and the server's stderr. To add the LSP messages, set the channel's log level to Trace ([Settings](../clients/vscode/README.md#settings)).
- **Neovim:** the server's stderr goes to Neovim's LSP log, as `ERROR` lines marked `"stderr"`. `:LspLog` opens the log with nvim-lspconfig on Neovim 0.11; otherwise, `:lua =vim.lsp.log.get_filename()` prints its path. To add the LSP messages, run `:lua vim.lsp.log.set_level("debug")` before reproducing the problem.

Report a failed check with the [bug report form](https://github.com/SaltedTan/virgil-language-server/issues/new?template=bug_report.yml), after checking the [known limitations](known-limitations.md).
