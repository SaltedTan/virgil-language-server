# Known limitations

This page lists what the v0.1 alpha doesn't do, or does only in part, for `0.1.0-alpha.4` and unreleased changes on `main`. See [editor compatibility](compatibility.md#editors) for feature availability by server version. Rename, completion, and signature help for calls still being typed came with `0.1.0-alpha.2`. `0.1.0-alpha.1` has none of them, so what this page says about them, such as [What rename refuses](#what-rename-refuses), applies from `0.1.0-alpha.2`. Type definition, inlay hints, document highlights, implementations, and the method-body fallback came with `0.1.0-alpha.4`, so what this page says about them applies from that release. Each item links to the page that owns the details. Check it before [reporting a bug](https://github.com/SaltedTan/virgil-language-server/issues/new?template=bug_report.yml).

## Features not yet implemented

- Completion suggests the keywords that can start where the cursor is, from the open document's text, even while the file has syntax errors. In a project, it also suggests the names in scope there, and after a `.`, the members of the receiver's type instead. It suggests nothing in comments or strings. A file that isn't open gets no suggestions ([Completion](architecture.md#completion)).
- Formatting and debugging are out of scope, and incremental analysis comes after v0.1 ([v0.1 scope](../README.md#v01-scope)).

## Code actions

Only the missing-semicolon quick fix exists. It checks the current first syntax
error and proves one token-end insertion by reparsing; other parse errors and
semantic diagnostics have no fix. A stale diagnostic, an insertion that leaves
the error at the same point, or a client without literal actions and versioned
edits gets no action. A bare CR before the semicolon error remains the parser's
first error, so it prevents the fix. The statement that the `;` would end
must start on the same line as the insertion. A missing `;` after a statement
that spans lines, such as a call whose arguments continue on the next line, an
`if (c)` or `match` arm whose body starts on the next line, or an assignment of
a lambda whose body spans lines, gets no fix even when inserting it would be
right: the parser may have read a later line into the statement, as when
`return` without its `;` reads a following `if (c)` as its value, and a parse
alone can't tell the two apart. The server finds the statement's start by
walking back over the parser's tokens, and it gives no fix where it can't tell
whether a brace closes a block or a lambda. On one line, it gives none when a
`;` earlier in the statement would parse as well: before an `if` that may be
an `if` statement that the parser read as a `return` value, or before a `++`
or `--` that may start the next statement, as in `x = y ++z`. So a `++` with
more code after it on its line, such as `i++ j++`, can lose a fix that would
be right. A layout field or a layout's size gets no fix either. There is no
fix-all or action on save ([Code actions](architecture.md#code-actions)).

## Semantic features need a project file

Without a `.virgil-lsp.json` that selects it, a document stays in [single-file mode](configuration.md#without-a-project-file), with no type errors, definition, type definition, inlay hints, hover, references, document highlights, implementations, type hierarchy, call hierarchy, signature help, or rename, and it contributes no workspace symbols. A project that lists `virgilDependencies` also needs a Virgil root: the one the editor sends, or else the library that a release archive bundles. With neither, as with a development build and no root set, or when the editor sends a root that isn't an absolute path, its project file gets a `MissingVirgilRoot` error and its documents stay in single-file mode ([The Virgil root](configuration.md#the-virgil-root)).

## Inlay hints

Inlay hints require a current project analysis. Method-body fallback omits hints inside the excluded body and maps hints and label links outside it to current text. Explicitly typed or unresolved locals, indirect calls, builtins, partial applications, tuple expansion, and redundant argument names have no hints. Settings take effect after a server restart; there are no insertion edits or hint resolution ([Inlay hints](architecture.md#inlay-hints)).

## Semantic tokens

Semantic tokens require a current project analysis. The server answers only requests for a whole document: it has no delta or range requests, so every answer holds all of a document's tokens, and an editor can't ask for only the lines it shows. While a project can't be analyzed, as when a syntax error is one that method-body fallback and current-text repair can't handle, a request fails with `ContentModified`, and VS Code and Neovim keep the tokens that they had, moved with edits: a name typed meanwhile keeps the grammar's color, and a changed declaration's uses keep their old color until an analysis succeeds. A file outside every project gets no tokens. `this`, a class's default `.new`, constructors, index methods, built-in types and their members, names in an excluded method body, and names after a file's 100,000th token get none. In VS Code, `auto` decides when the server starts, so enabling or disabling the `titzer.virgil` extension takes effect at the server's next start; with `on` beside `titzer.virgil`, VS Code shows the tokens of whichever extension registered its provider last, as the [VS Code coexistence check](../clients/vscode/README.md#with-the-virgil-extension-installed) observed, and neither extension controls which that is ([Semantic tokens](architecture.md#semantic-tokens)).

## Types without source declarations

Type definition returns no location for built-in and structural types, including strings, arrays, ranges, tuples, and functions, or for unresolved types. It never follows their element types. `Box<Foo>` targets `Box`; the documented `Ref<L>` exception targets layout `L` ([Type definition](architecture.md#type-definition)).

## Selection ranges

Selection ranges use the current open document only; closed documents have none. Chains contain tokens, bracket-group contents and delimiters, completed declarations, and the document, with no separate expression or statement ranges. A parse error removes syntax extents crossing or following the first error; lexical recovery supplies only trustworthy tokens and stops at an invalid literal, omitting operators that need parser context and any number directly after a `-`. Requests above 100 positions are rejected, and chains deeper than 128 levels retain their innermost 127 and the document ([Selection ranges](architecture.md#selection-ranges)).

## Folding ranges

Folding uses brace blocks and multiline comments from the open document's current syntax; closed documents have no ranges. It provides no indentation, import, or `region` marker folds. A parse error removes folds crossing or following the first error, and an error without an exact byte offset removes all folds. Replies contain at most 10,000 ranges or the client's smaller limit, keeping the outermost ranges first ([Folding ranges](architecture.md#folding-ranges)).

## No error-tolerant parsing

- After a file has been analyzed without a syntax error, a later syntax error strictly inside one method or constructor body can preserve definition, type definition, inlay hints, implementations, hover, references, highlights, and type errors outside that body. The whole damaged body gets no semantic answer, and reference and highlight lists can be partial. The edit must preserve lexical state and balance braces in both texts. An unclosed brace, a header or field-initializer edit, or an interval spanning bodies cannot use this fallback. Unterminated strings, byte literals, and block comments are ineligible even when scanning recovers inside the interval ([Method-body fallback](architecture.md#method-body-fallback), [ADR-0008](decisions/0008-method-body-fallback.md)).
- Fallback needs cached parseable text from the same project context. Files without a cached predecessor, including cold starts and evicted entries, are not substituted from the cache, though an open one can still be repaired (below), and closed files with syntax errors are not substituted at all. If any effective input still fails to parse, Aeneas does not type-check the project: its type errors disappear, definition, type definition, hover, references, document highlights, inlay hints, and implementations return nothing, and rename is refused. The global cache is limited to 4 MiB including metadata. A cached disk text larger than the 1 MiB open-document limit cannot be reparsed for fallback. Rename, prepare rename, and preflight always refuse a substituted snapshot, even outside the damaged body; completion and signature help keep their own cursor-repair rules below. Broader error tolerance remains in [M6](../ROADMAP.md#m6--error-tolerance-and-incrementality-48-weeks-evidence-driven).
- An open file with a syntax error that fallback can't substitute, such as a file opened with the error already in it or one whose cached text was evicted, is analyzed with the method or constructor body that holds the parser's first error emptied: every byte between the body's braces, except CR and LF, becomes a space, so nothing else in the file moves. If the file still fails to parse, the body that holds its next error is emptied too, at most two bodies. This covers an error that the parser first reports on the next line, as when that line continues an unfinished expression, and errors in two bodies. Such a file keeps the same answers outside those bodies as fallback gives, with the same gaps: each emptied body gets no semantic answer, reference and highlight lists can be partial, workspace symbols skip the file, and rename is refused. No string, byte literal, or block comment may be left open, so an unterminated literal or comment is not repaired. A file with one missing `{` is repaired only where its indentation shows which brace is missing: every other brace pair in the file must agree with the indentation, with a tab reaching the next multiple of 8 columns, the method's header must be on one line, with no comment between its first word and its parameters, and the missing brace must be a control statement's `{`, such as an `if`'s or a loop's. The method's body is then emptied, and nothing else moves. A lost `{` in a method with a plain header, such as `def g() {`, after a declaration without a body that could be a method's, such as `def size() -> int;`, isn't repaired unless a private method or a constructor lies between them, since the method could be a local function of that one, had it lost its `{` before the `;`; nor is a lost `{` where the method could instead have ended at an earlier `}` indented like a statement, before a member whose own `{` is missing. This repair trusts the indentation. In a file whose own indentation disagrees with its braces near the missing `{`, such as a method whose first block's `}` is written as deep as the method, with a local function after it written as deep too, the repair can take the wrong `{` for the missing one, and answers outside the emptied body, such as a definition, hover, or references, can point at the wrong declaration. You can tell from the editor: near the error, the brace structure and the indentation disagree, as with a `}` that lines up with a line other than the one its `{` is on. Fixing the missing brace, or the indentation, restores exact answers. A file with one missing `}` is repaired only where every place that `}` could have been, up to the end of the line of the first syntax error, leaves it in the same method or constructor: the missing `}` must be a block's inside that method, such as a match case's block or an `if`'s in a lambda, and the method's body is then emptied. A method's own missing `}` isn't repaired, since the method could end wherever its `}` could go; nor is a missing `}` whose first syntax error is directly in the outermost block that the file leaves open, as when a later method parses as a local function until the end of the file, one in a file with a second syntax error, or one whose places would take more than 16 parses to try. This repair doesn't read the indentation. Nor are a file whose indentation disagrees with its braces elsewhere, such as one indented with tabs in some lines and four spaces per level in others, two missing or extra braces, or an error in a declaration header or a field initializer, between members, as where a method's header was deleted but its braces kept, or in a third body. The project then gets no semantic answers anywhere, as before ([Current-text repair](architecture.md#current-text-repair), [ADR-0009](decisions/0009-current-text-repair.md), [ADR-0010](decisions/0010-analyze-unrepairable-files.md)).
- Signature help shows a call that is still being typed, such as `f(a,` or an unclosed `f(`, only when the same fix at the cursor as completion's makes the file parse. That includes a `(` that your editor closed at once, as in `f()` at the end of a line with the cursor inside: the fix ends the statement after the `)`. Anything else gets nothing: a syntax error elsewhere in the file or in another file of the project, or a missing `}`, as in a lambda body you are still typing. A complete call with a semantic error, such as `f();` with the cursor inside, does parse, and gets its signature ([Incomplete calls](architecture.md#incomplete-calls), [ADR-0006](decisions/0006-incomplete-code-repair.md)).
- Workspace symbols omit every declaration in a file whose analyzed text substitutes a cached or repaired method body, including declarations outside that body. Another loaded project's current, unsubstituted analysis can still supply the file's symbols; otherwise they return after the file parses again. Other files in the substituted snapshot can still appear in searches ([Workspace symbols](architecture.md#workspace-symbols)).
- Completion suggests names or members in code that doesn't parse only when one repair at the cursor makes it parse: a name, the closing `)`, `]`, or `>` of what is open in the innermost block that the text doesn't already have, and a `;` where the statement ends. An editor that closes a delimiter as soon as it is typed leaves the closers after the cursor, as in `var n = Util.add(|)`, and the repair puts the `;` after them, so the arguments still get names. Anything else gets keywords only, or nothing after a `.`: a syntax error elsewhere in the file or in another file of the project, or a missing `}`, as in a lambda or `if` body you are still typing. The type checker gives up after 15 errors, and completion then suggests names only where it got to: in a file that has lost declarations other files need, such as one cut off at the cursor, the method you are typing in may get keywords only ([Completion](architecture.md#names), [ADR-0006](decisions/0006-incomplete-code-repair.md)).
- Completion follows the type checker's rules for which names a spot can use, not for their types. In a match on an `int`, it suggests every constant a case can compare, whatever its type, and in a component's field initializer it can suggest a field whose type the compiler cannot infer there because the fields' initializers depend on each other in a cycle ([Completion](architecture.md#names)).
- With `-lang:descriptors` enabled, completion of plain names doesn't suggest a class's descriptor fields. After a `.`, as in `b.`, it does ([Completion](architecture.md#completion)).
- If document-symbol parsing fails, the outline is empty, never stale or truncated. That parse normalizes carriage returns, so a CRLF file can have syntax diagnostics and still an outline. When analysis substitutes a cached or repaired method body for that file, its current-text outline has no snapshot signature details, even outside the body, because the analyzed declaration offsets belong to the effective text. Unsubstituted files keep their details ([Document symbols](architecture.md#document-symbols)).
- An analysis stops at 15 errors, and an Information diagnostic (`ErrorLimit`) then says that errors elsewhere may be missing. During method-body fallback or current-text repair, any error in an excluded body suppresses that notice, even if the last error is outside the body. The cached body's errors, or the missing-return error that an emptied body of a method returning a value gets at its opening brace, can consume the limit and hide later errors, so a partial diagnostic set can arrive without a limit notice; when no errors are excluded, the notice stays. Aeneas rejects carriage returns, as `v3c` does, with one error per CRLF line, so a single CRLF file reaches the limit. Convert CRLF files to LF, which WSL users' checkouts may need ([error limit](architecture.md#semantic-diagnostics)).

## Document highlights

Document highlights use one kind per occurrence, so a compound assignment or increment is Write even though it also reads the value. A request with more than 10,000 highlights in its document fails instead of returning a partial list ([Document highlights](architecture.md#document-highlights)).

## Implementations

Implementations come only from the document's active project, so a subclass in another program that shares the file isn't listed. With semantic errors, they list only what the type checker resolved: a class whose superclass doesn't resolve has no base, an inheritance cycle loses its rejected superclass edge but keeps its other implementation relationships, and after 15 errors later declarations can be missing. A request with more than 10,000 implementations, or more than 4 MiB of their locations, fails instead of returning a partial list ([Implementation](architecture.md#implementation)).

In code with errors, a type parameter named like a builtin type, such as `int` in `class C<int> { var x: Missing<int>; }`, can make implementation answer an empty list at a use of it that doesn't resolve, the inner `int` there, where definition, type definition, and hover answer nothing. Neither answer offers a destination ([Implementation](architecture.md#implementation)).

## Type hierarchy

Type hierarchy covers classes, variants, and variant cases only; components, enums, methods, and every other declaration have none, and no request lists a method's overrides one level at a time. It shows one level per request, as the protocol asks, and comes from the same class hierarchy as implementations, so their limits apply: a subtype in another program that shares a file isn't listed, a class whose superclass doesn't resolve has no supertype, an inheritance cycle loses its rejected superclass edge but keeps its other supertype and subtype relationships, and after 15 errors later declarations can be missing. A request expanding an item looks in the item's own file's project, which in a file shared by several programs can be another program than the one the hierarchy started in. An item finds its declaration again only where its name was, by its file, its name's position, kind, name, and a case's variant, so after an edit that changes any of them, including text inserted before the declaration in its file, which moves it, the item expands to nothing until the hierarchy is shown again. Details are left out in a file whose broken method body was replaced by its cached text. A request with more than 10,000 subtypes, or more than 4 MiB of their items, fails instead of returning a partial list ([Type hierarchy](architecture.md#type-hierarchy)).

## Call hierarchy

Call hierarchy shows only direct calls that verification bound to a method or an explicit constructor, so some calls are missing ([Call hierarchy](architecture.md#call-hierarchy)):

- A virtual call is listed as a call of the method of the receiver's static type, never of the overrides that may run instead; [implementation](architecture.md#implementation) lists those.
- Calls through function values aren't listed: a parameter, local, or field that holds a function, a call of a call's result, and a function passed as a value, such as `twice` in `apply(twice, 3)`, which is no call of `twice`. A partial application such as `sum(_, 1)` makes a function value and isn't listed as a call either.
- A construction of a class without an explicit constructor, such as `Plain.new()`, calls no declaration, so it isn't listed, and the hierarchy can't be prepared at its `new`. Variant and data-type constructions, builtins, operators, and index operations such as `a[i]` aren't calls either, even with an index method, though a named call such as `a.[](i)` is.
- A constructor's `super(...)` clause isn't kept as a call by the parser, so a constructor's call of its superclass's constructor is missing.
- A call in a superclass's arguments in a class's header, as in `class B extends A(f())`, has no method, constructor, or field around it, so it has no caller and isn't listed.
- A call whose callee doesn't resolve, in code with errors, isn't listed, and after 15 errors later declarations' calls can be missing.

A call in a field's initializer is listed with the field as its caller; the hierarchy can't be prepared at a field, though, even one that holds a function. Fields, locals, and parameters are never callees. Calls come only from the active project of the request's file, so a caller in another program that shares a file isn't listed. An item finds its declaration again only where its name was, by its file, its name's position, kind, and name, as a type hierarchy item does, and only inside the same enclosing declarations, so after an edit that moves the declaration, or puts a member of the same name from another class in its place, it expands to nothing until the hierarchy is shown again. In a file whose broken method body was replaced, calls in that body are missing in both directions and details are left out. Incoming calls read again and parse every file that calls the function, so a function called from many files takes longer, about 80 ms for Aeneas's `StringBuilder.puts`, with 655 calls in 76 files ([Benchmarks](benchmarks.md#call-hierarchy)). A request with more than 10,000 calls, or more than 4 MiB of them, fails instead of returning a partial list.

## Member completion

After a `.`, completion suggests the members that the type checker would accept for the receiver's type, and nothing else: no keywords, and no names in scope. It doesn't guess, so some places get an empty list ([Member completion](architecture.md#member-completion)):

- **After a number.** A `.` after a number, as in `1.` or a tuple element's `t.0.`, gets nothing, because the server can't tell it from a number such as `1.5` being typed. Write `(t.0).` to get the element's members.
- **Unknown receivers.** A receiver whose type the type checker couldn't work out, such as a misspelled name or a call to a method that doesn't exist, gets nothing.
- **Unreached code.** Code that the type checker didn't reach before its error limit gets nothing, as with names. Neither do the arguments of a call to a function that doesn't exist yet, as in `missing(a.`: the type checker skips them.
- **Layout fields as values.** With the cursor before an existing layout field's name, as in `L.f` used as a value, nothing is suggested, because the type checker records nothing there that shows it looked up the layout. With `|` marking the cursor, `L.|`, `L.|size`, and `L.|f.offset` suggest the layout's members; `L.f.|offset` suggests the field's `offset` member.
- **Integer values.** A value of an integer type, such as `x.` for an `x: int`, has no members to suggest. `int.max`, `int.view`, and the other integer members belong to the type, so `int.` suggests them.
- **Type positions.** Where a type goes, as in `var s: Flag.` before `set`, nothing is suggested; members are suggested only in expressions.
- **Operators.** Casts, queries, comparisons, and index methods, such as `int.!`, `int.?`, `==`, and `[]`, are written with symbols, not names, so they aren't suggested.
- **Pointers.** Pointer members aren't suggested, because the server analyzes programs without a compilation target, and Aeneas defines pointers only for one.
- **Strings.** A member's description shows types as the type checker resolved them, so a `string` appears as `Array<byte>`.

## Stale results

Semantic results come from the newest analysis of the document's project. An analysis starts 200 ms after the last edit, or at once on open, save, or close ([scheduling](architecture.md#semantic-diagnostics)).

- **Diagnostics.** After an edit, a file's type errors disappear until the next analysis completes; its syntax errors follow the edit at once. An analysis that a later edit made stale is discarded, not published.
- **Definition, type definition, hover, references, document highlights, implementations, type hierarchy, call hierarchy, and signature help for text that parses.** A request against a stale or missing snapshot waits for the pending analysis, then answers from it. The answer is empty if that analysis is stale too, or if the document changed while the request waited. Without a pending analysis, for example after a failed one, the answer is empty at once ([Definition](architecture.md#definition), whose rules [Hover](architecture.md#hover), [References](architecture.md#references), [Document highlights](architecture.md#document-highlights), [Implementation](architecture.md#implementation), [Type hierarchy](architecture.md#type-hierarchy), [Call hierarchy](architecture.md#call-hierarchy), and [Signature help](architecture.md#signature-help) share). Calls still being typed follow the separate [incomplete-call scheduling rules](architecture.md#incomplete-calls).
- **Completion.** Names and members need an analysis of the whole project for each new cursor position or change to the document's text, about 130 ms for the Aeneas sources, after any analysis that is already running. A version-only change at the same cursor reuses the last reply. Requests that need only keywords are answered at once; requests that need names wait and receive both together. A newer request replaces an older one that hasn't started; the older one gets only keywords, or an empty list after `.`. See [Completion](architecture.md#names) for the reuse and invalidation rules.
- **Rename.** A rename waits for a pending analysis as definition does, and is refused if its document changed while it waited, or if any document or the project's files changed while its edits were checked; try it again then ([Rename](architecture.md#rename)).
- **Compiler traps.** On unreleased `main`, inheritance cycles report diagnostics and retain semantic answers elsewhere in the project, with the rejected superclass edge ignored. Recursive generic unification, such as `class S<T> {} class A extends S<A> {} class B extends S<B> {}` followed by `[a, b]` for values of `A` and `B`, still overflows the analysis worker's stack and prevents new semantic answers until the input changes ([crash paths, row 6](aeneas-crash-paths.md)).
- **Failed analyses.** When an analysis fails, for example because the worker crashed, ran past 10 seconds, or returned a result over the size budget, the published diagnostics stay as they were, and the server logs a warning. The first failure also shows a warning message; later ones are only logged until an analysis succeeds again. The server doesn't retry: the next open, edit, save, close, or file event starts a new analysis, in a new worker after a worker failure ([failures](architecture.md#semantic-diagnostics), [restart policy](decisions/0004-analysis-worker-process.md#restart-policy)).
- **Changes outside the editor.** The server learns about them only from the client's file events. Clients without file events, such as Neovim 0.11.6 on Linux and in WSL 2 with the shipped configurations, see them when a project is next used; restart the server after a checkout that adds or removes files ([Changes on disk](configuration.md#changes-on-disk)).

## Supported program size

The largest program tested is the Aeneas sources and their dependencies. [Supported program size](decisions/0004-analysis-worker-process.md#supported-program-size) owns its measured result size, the regression bound, and capacity estimates. The result's size, not a line count, is the main limit.

A project's program may also select at most 1,024 files and 4 MiB of paths and source ([Patterns](configuration.md#patterns)), and each analysis gets the worker's 384 MB heap and 10 seconds. A project over the file or source limit gets a configuration diagnostic. A program whose result is over budget gets no semantic results: its analyses fail with a warning. Analyze fewer files together, as a smaller project; a larger `WORKER_HEAP` doesn't raise the result budget.

Every analysis checks the whole program again. For the Aeneas sources, diagnostics arrived about 220 ms after a save on the measured machine ([measurements](architecture.md#semantic-diagnostics)).

Open documents share 1 MiB of text and metadata. Beyond that, the server shows a warning and ignores the open or edit; close other documents, then reopen the document or edit it again ([Document store](architecture.md#document-store)).

## Platforms and editors

- Supported hosts are Linux x86-64, including SSH remotes, and macOS on Apple Silicon, which runs the Intel (`x86-64-darwin`) build under Rosetta 2 ([host platforms](compatibility.md#host-platforms)).
- WSL 2 on x86-64 Windows is best effort. The Linux build is expected to run inside it, but nobody tests it there, and CI runs only on Linux itself ([host platforms](compatibility.md#host-platforms)).
- Native Windows, WSL 1, and Linux arm64 aren't supported. On Windows, use WSL 2, on a best-effort basis; the VS Code extension refuses to start natively on Windows ([startup checks](../clients/vscode/README.md#startup-checks)). macOS on Intel uses the same build but is untested.
- Apple Silicon needs Rosetta 2 until Virgil can build for `arm64-darwin`. Apple has said that macOS 27 is the last release with full Rosetta 2 support ([ADR-0003](decisions/0003-supported-platforms.md)).
- Neovim needs version 0.11 or later, and VS Code 1.91 or later. See the [LazyVim test](../test/e2e/lazyvim/README.md#ci) for its CI coverage; for `0.1.0-alpha.3`, the [LazyVim test](../test/e2e/lazyvim/README.md) passed on Linux and macOS ([editors](compatibility.md#editors)). In LazyVim, noice.nvim drops servers' `window/showMessage` warnings, such as "Invalid project file …", although the diagnostics still appear; [the LazyVim setup](../editors/nvim/README.md#lazyvim) shows how to turn its handler off. The [manual test matrix](manual-testing.md) records which editor and platform combinations were tried.
- In VS Code, restarting the server while an edit is still waiting to be sent to it, as **Virgil: Restart Language Server** or the recovery after a crash can, may log `Delivering pending changes failed: TypeError: this.task is not a function` in the "Virgil Language Server" output channel. It is a bug in `vscode-languageclient`, the library that the extension uses ([microsoft/vscode-languageserver-node#1916](https://github.com/microsoft/vscode-languageserver-node/issues/1916)), and loses nothing: after the restart, the client sends the server every open buffer again, including unsaved text, and later edits as usual ([Extension Host test](../clients/vscode/README.md#extension-host-test)).

## Installation

- The server executables are unsigned and not notarized. On macOS, a browser marks a download as quarantined, and macOS may then refuse to run it: download with `curl` or `gh`, or remove the attribute as [Installing on macOS](releasing.md#macos) shows. [Verifying a download](releasing.md#verifying-a-download) checks an archive against `SHA256SUMS`.
- Nothing is published to a package manager, the Visual Studio Marketplace, or Open VSX. Install the extension from its platform VSIX by hand ([Installing from a VSIX](../clients/vscode/README.md#installing-from-a-vsix)), and the server for Neovim, LazyVim, or an external-server setup from a release archive ([Installing](releasing.md#installing)). VS Code doesn't update an extension installed from a VSIX: install the next release's VSIX to update.
- Release archives bundle only Virgil's `lib/`. Projects selecting `rt/`, `aeneas/`, or other sources outside it still need a client-supplied checkout at the revision that `virgil-lsp --version` prints. Development builds have no bundle by default. Missing or mismatched bundles leave no root, and invalid client overrides block fallback ([The Virgil root](configuration.md#the-virgil-root)).

## Protocol numbers and synchronization

- JSON numbers must be signed 32-bit integers. A fraction, exponent, or out-of-range integer anywhere in an admitted request to a supported method, including unused `initializationOptions`, gets `InvalidParams` (-32602) with the request's original ID. The dispatcher ignores notifications containing these numbers, except `exit`; document synchronization notifications admitted by the lifecycle also log a warning. Numeric request IDs outside that range instead get `InvalidRequest` (-32600) with a null ID. This is a `JsonValue` representation limit, including for otherwise valid free-form LSP data ([JSON rules](architecture.md#json-limitations-and-workarounds), [lifecycle admission](architecture.md#lifecycle)).
- The server negotiates full synchronization. A `didChange` containing a range or `rangeLength` is ignored and logged as “incremental changes are not supported,” with no notification reply. The overlay's text and version stay unchanged. An empty `contentChanges` with a newer version is accepted as a version-only update; subsequent versioned rename edits carry that version ([document synchronization](architecture.md#document-store)).

## What rename refuses

[Rename](architecture.md#rename) is deliberately conservative: it refuses rather than risk an edit that changes what the program means, and its reason says why. [Prepare rename](architecture.md#prepare-rename) lists the rules for which names can be renamed, and [Rename](architecture.md#rename) the rules for new names and edits.

- Start rename or prepare rename from an open editor document. Requests from closed files are refused because their positions can move on disk without a file notification; the rename can still edit other closed files ([request document](architecture.md#rename)).
- It refuses to rename anything while the project's analysis has any error, a parse error or a semantic one, anywhere in the project. A use that the verifier did not resolve would be missed ([eligibility](architecture.md#prepare-rename)).
- It analyzes the whole program again with the edits applied before it replies, so a rename takes about as long as an analysis of the project ([measurements](architecture.md#rename)). One rename is checked at a time; another sent meanwhile is refused until the first is answered ([scheduling](architecture.md#rename)).
- It renames a method together with its override family: the methods that it overrides, and every method that overrides one of them, directly or through others, in subclasses and variant cases, which it finds from the class hierarchy that verification records. Methods that only share the name, in unrelated classes, components, or files, keep it. It refuses the rename if any method of the family is in a dependency or a library under the Virgil root ([eligibility](architecture.md#prepare-rename)).
- It refuses a new name that would change which method a method overrides, which a check of the uses alone would miss: renaming a base class's method to a subclass method's name, or the reverse, would make one override the other while every use still binds as before, and a method renamed in a class between two others can come between a method and the one it overrides. The preflight compares each method's overridden method before and after the edit; a new name that only an unrelated method has is accepted ([comparison](architecture.md#rename)).
- It refuses a name token that declares two things, each with uses: `x` in `class D(x: int) extends Base(x)` names both the class parameter and its field, and one token cannot take two new names ([shared name tokens](architecture.md#prepare-rename)).
- It refuses packings and their parameters, constructors, operators, and the navigation aliases `this` and `.new`, which it never edits when it renames their class ([eligibility](architecture.md#prepare-rename)).
- It edits only the project's own sources: not a dependency, a library under the Virgil root, or a file that another loaded program also selects ([ownership](architecture.md#prepare-rename)).
- The check of which loaded programs own the renamed files has a budget of 8,000,000 matching steps. A workspace with so many project patterns that the check exhausts it gets "the workspace has too many project patterns to check which programs own the renamed files" ([ownership budget](architecture.md#prepare-rename)).
- That check compares paths as text, without resolving them. Another program that reaches the same file through a hard link, or, on a case-insensitive file system, through a directory spelled with different case, is not found, so the rename can edit a file that program also analyzes ([path identity](architecture.md#uri-identity-on-linux-and-macos)).
- It refuses a new name that would make any use bind differently, even if the program still verifies, a new name that is a keyword, `this`, or not an identifier, and one longer than 255 bytes ([new names](architecture.md#rename)).
- A rename has at most 10,000 edits and a reply of at most 4 MiB of encoded JSON. A larger one is refused whole, never sent in part ([edits](architecture.md#rename)).
- The editor must accept versioned edits (`workspace.workspaceEdit.documentChanges`), so that an edit to a document that changed meanwhile is refused. VS Code does. Neovim 0.11.6 applies them but omits them from its capabilities, so the shipped [Neovim configurations](../editors/nvim/README.md#rename) declare them for it, and Neovim checks the version of only the first document of an edit ([client requirements](architecture.md#rename)).
- It never edits comments, strings, `#packing` hints, or file names.

## Names that definition, type definition, hover, references, and document highlights don't cover

Only the uses that the [occurrence index](architecture.md#compiler-adapter) records resolve; it owns the full list. In particular:

- Builtin types, such as `int`, `Array` in `Array<Foo>`, `set` in `E.set`, and `Ref` in `Ref<L>`, have no definition, references, or document highlights. Hover shows the type of a builtin used in an expression, such as `.length`, but nothing for a builtin type in a type position ([Hover](architecture.md#hover)).
- The letters of a bit pattern, such as `0b_aabb`, and the names in a `#packing` hint on a variant case aren't indexed ([#111](https://github.com/SaltedTan/virgil-language-server/issues/111)).
- Hover shows nothing at a keyword, a literal, or an unresolved name, and doesn't show the type of a larger expression.

## Signature help

[Signature help](architecture.md#signature-help) shows the signature that the analysis recorded for the call around the cursor, and owns the details. In particular:

- A signature's label is cut at 256 bytes and then ends with `…`. Only the parameters that the cut label holds are listed, and a later active parameter is reported as its index past the list.
- A call with more arguments than its function has parameters, which is a type error, reports the parameter index past the last, as does a cursor after a trailing comma that follows as many arguments as there are parameters, as in `add(1, 2,)`.
- How a client shows an active parameter past the list varies: LSP 3.17 specifies that it defaults to parameter 0, VS Code highlights no parameter, and Neovim 0.11.6 highlights the last.
- A client without `labelOffsetSupport` gets each parameter's label as a string, and finds it in the signature's label itself: in `(int, int) -> int`, both parameters are `int`, and such a client may highlight the first for either. VS Code and Neovim both support label offsets, which are exact.
- A call without a known signature gets nothing: an unresolved callee, and the calls in its arguments, which verification doesn't check either.
- A call you are still typing needs its own analysis of the project, about 140 ms on the Aeneas sources, as a completion does. An operator-named member's call is found like any other: a cast's `B.!(`, a type test's `B.?(`, a builtin operator's `int.+(`, or a variant case's `V.One.!(`, alone or within another call's arguments, gets that call's signature. A cast's or a generic call's inferred types show `?` until you type the argument that infers them: `B.!(|` gets `? -> B`, and `id(|` gets `def id(v: ?) -> ?`. It gets nothing in an if expression's first argument, as in `if(f(` while you type `f`'s arguments, since the type checker skips an if expression with too few arguments. After `>`, as in `a > (b`, and in a constructor's `super(` clause, it gets nothing rather than the call around the cursor ([Incomplete calls](architecture.md#incomplete-calls)).
- There is no documentation, since the analysis doesn't keep doc comments.

## Crashes in the compiler front end

Some inputs crash or hang the pinned Aeneas front end. [Aeneas crash paths](aeneas-crash-paths.md) lists the known ones and how each is contained. Whole-program analysis runs in a separate worker process, so a crash fails that analysis, a hang is stopped after 10 seconds, and a new worker runs the next analysis (see [Stale results](#stale-results)). Single-file parsing runs in the server, with guards for every known parser crash; none of the known inputs stops the server. Report a new one with the smallest input that shows it.
