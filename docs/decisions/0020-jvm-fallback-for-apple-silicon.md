# 0020. Ship a JVM fallback for Apple Silicon without Rosetta 2

- Status: Accepted; amends [ADR-0003](0003-supported-platforms.md)
- Date: 2026-11-21, recording the maintainer's decision of 2026-11-03 and the launch settings adopted on 2026-11-21
- Discussion: [#191](https://github.com/SaltedTan/virgil-language-server/issues/191), [#466](https://github.com/SaltedTan/virgil-language-server/issues/466)

## Context

Apple has said that general-purpose Rosetta works through macOS 27, and that macOS 28 keeps only a subset of Rosetta for older games ([Apple support](https://support.apple.com/en-us/102527), summarized in [#191](https://github.com/SaltedTan/virgil-language-server/issues/191#issuecomment-6469628182)). The server and worker are `x86-64` binaries, so the default macOS assets need Rosetta 2 on Apple Silicon ([ADR-0003](0003-supported-platforms.md)).

The pinned Virgil's targets are `x86-64-linux` and `x86-64-darwin`; there is no `arm64-darwin` target ([ADR-0003](0003-supported-platforms.md)). [ADR-0003](0003-supported-platforms.md) named Virgil's `jar` target as the fallback if Rosetta 2 were phased out before `arm64-darwin` arrived, but left it unvalidated. The comparison from pin `57318d37` to upstream master `1716427f` found no Darwin ARM64 implementation; `bin/dev/sense_host` recognizing `arm64-darwin` is host detection, not a compiler target ([#191](https://github.com/SaltedTan/virgil-language-server/issues/191#issuecomment-6469628182)).

[ADR-0003](0003-supported-platforms.md) expected the switch to native `arm64-darwin` to be limited to the build scripts and release packaging, because of the adapter boundary ([ADR-0002](0002-pinned-virgil-adapter-boundary.md)). [#191](https://github.com/SaltedTan/virgil-language-server/issues/191) recorded that reusing the semantic adapter doesn't make this a packaging-only change: the code also depends on `HostOs` system calls, the native parser's stack guards (whose JVM counterpart is [ADR-0017](0017-jvm-parser-stack-guard.md)), direct pointer hashing, and the worker's semispace and runtime metrics ([ADR-0004](0004-analysis-worker-process.md)). The probe confirmed the work: on the JVM target, five native-only spots outside `src/os/` needed a per-target component (the parser's stack guard, pointer word loads in hashing and URI comparison, and the worker's heap size, forced collection, and collection statistics), a JVM `HostOs` took 146 lines, and Aeneas's front end compiled unchanged ([#191](https://github.com/SaltedTan/virgil-language-server/issues/191#issuecomment-6601944751)).

A probe on 2026-11-03, at `139db845` on Linux x86-64, found the JVM target feasible for both executables. It also found native `arm64-darwin` unclear and likely large: upstream has an arm64 code generator and an arm64-linux runtime, which register only in a development build. It has no arm64 Mach-O output, no Darwin arm64 system-call or signal stub, no `rt/arm64-darwin`, and no code signing, and the backend uses register x18, which Darwin reserves ([#191](https://github.com/SaltedTan/virgil-language-server/issues/191#issuecomment-6601944751)). A follow-up on an Apple M4, macOS 27.0.1, ran the JVM build with an arm64-only OpenJDK, so it ran natively, without Rosetta, and passed the benchmark's semantic checks ([#191](https://github.com/SaltedTan/virgil-language-server/issues/191#issuecomment-6603166249)).

The upstream JVM runtime has no processes, pipes, poll, or directory listing, and a JVM program can't call Java APIs directly. The probe used its own copy of the runtime class, so the server still started the worker as a separate process over pipes ([ADR-0004](0004-analysis-worker-process.md)). A clean implementation needs a supported way for the JVM target to call host functions ([#191](https://github.com/SaltedTan/virgil-language-server/issues/191#issuecomment-6601944751)).

[#191](https://github.com/SaltedTan/virgil-language-server/issues/191) proposed deciding the path by 2027-01-31 and shipping a local release target by 2027-05-31. The maintainer decided on 2026-11-03 to fund the JVM path as the fallback release target for Apple Silicon without Rosetta 2, and not to fund native `arm64-darwin` now ([#191](https://github.com/SaltedTan/virgil-language-server/issues/191#issuecomment-6602928854)). The plan followed in dependency order: a JVM host runtime bridge ([#459](https://github.com/SaltedTan/virgil-language-server/issues/459)), JVM builds of both executables ([#460](https://github.com/SaltedTan/virgil-language-server/issues/460)), bounded deep parsing ([#461](https://github.com/SaltedTan/virgil-language-server/issues/461)), preserved crash classification ([#462](https://github.com/SaltedTan/virgil-language-server/issues/462)), memory measurements ([#463](https://github.com/SaltedTan/virgil-language-server/issues/463)), packaging ([#464](https://github.com/SaltedTan/virgil-language-server/issues/464)), and CI and release ([#465](https://github.com/SaltedTan/virgil-language-server/issues/465)) ([#191](https://github.com/SaltedTan/virgil-language-server/issues/191#issuecomment-6618907630)).

## Decision

The supported platforms stay those of [ADR-0003](0003-supported-platforms.md). This record adds the JVM fallback to the Apple Silicon decision and corrects ADR-0003's expectation that only the build scripts and release packaging would change; Linux x86-64 and Intel macOS support don't change.

1. **`darwin-arm64` keeps the Intel build under Rosetta 2 as the default.** While macOS still includes Rosetta 2, the default `darwin-arm64` VSIX and the macOS archive stay the `x86-64-darwin` build run under Rosetta 2. On the M4 it started in 4.8 ms against the JVM build's 159.0 ms, and the Aeneas server's sampled peak memory was 203.0 MiB against the JVM build's 405.2 MiB ([#191](https://github.com/SaltedTan/virgil-language-server/issues/191#issuecomment-6603166249), [#464](https://github.com/SaltedTan/virgil-language-server/issues/464)).
2. **The JVM build ships as an additional, preview release asset.** It has its own `virgil-lsp-<version>-jvm-arm64-darwin.tar.gz` archive and `darwin-arm64-jvm` VSIX, built and tested in every release, until macOS drops Rosetta 2. VS Code doesn't select the JVM VSIX for users; it is installed from its file. Making the JVM build the default is a later decision, tied to Apple's Rosetta timeline ([#191](https://github.com/SaltedTan/virgil-language-server/issues/191#issuecomment-6618907630), [#464](https://github.com/SaltedTan/virgil-language-server/issues/464), [release guide](../releasing.md#the-jvm-build-for-apple-silicon)).
3. **The JVM assets bundle their Java runtime.** They redistribute Eclipse Temurin 21 LTS, jlinked with only the `java.base` module for `darwin-arm64`, pinned at release `21.0.13+9` by version and SHA-256, with its `legal/` notices and Adoptium's corresponding source archive attached to the same release. The assets therefore need neither Rosetta 2 nor a separately installed Java runtime ([#464](https://github.com/SaltedTan/virgil-language-server/issues/464#issuecomment-6678602912), [PR #482](https://github.com/SaltedTan/virgil-language-server/pull/482), [release guide](../releasing.md#the-jvm-build-for-apple-silicon), [third-party notices](../../THIRD_PARTY_NOTICES.md#eclipse-temurin-java-runtime-jvm-assets-only)).
4. **The runtime costs are bounded by measured launch settings, not by the Linux budgets.** The maintainer adopted the [JVM memory note](../testing-notes/jvm-memory.md#proposal-adopted-on-2026-11-21)'s proposal on 2026-11-21: the server runs with `-Xmx128m -XX:+UseSerialGC`, the worker with `-Xmx256m` on the default collector (G1), and neither passes `-Xss`. The documented envelope is 1 GiB of resident memory for the two processes together, 384 MiB for the server and 640 MiB for the worker ([#463](https://github.com/SaltedTan/virgil-language-server/issues/463#issuecomment-7054681655), [PR #593](https://github.com/SaltedTan/virgil-language-server/pull/593)). A re-measurement on the `macos-15` runner the same day, with the packaged archive and its bundled runtime, put the Aeneas high-water marks at 211.5 MiB for the server, 318.4 MiB for the worker, and 529.9 MiB combined ([#463](https://github.com/SaltedTan/virgil-language-server/issues/463#issuecomment-7054681655), [JVM memory note](../testing-notes/jvm-memory.md#ci-re-measurement-on-macos-15-2026-11-21)). The Linux budgets in [ADR-0016](0016-performance-budgets.md) and [performance budgets](../performance-budgets.md) remain Linux x86-64 only; the JVM figures change neither them nor the native build's defaults, and no performance parity is claimed for fresh analysis ([#463](https://github.com/SaltedTan/virgil-language-server/issues/463), [JVM memory note](../testing-notes/jvm-memory.md)).
5. **The remaining costs are documented rather than hidden.** On the M4, the JVM build's startup to the `initialize` reply was 159.0 ms median against Rosetta's 4.8 ms. First analyses were 5–7.5 times slower on the small and util projects and 1.9 times slower on Aeneas; once warm, Aeneas's reused analysis, rename, completion miss, and semantic diagnostic were within the run's noise of Rosetta or faster, and peak sampled RSS was about twice Rosetta's on Aeneas ([#191](https://github.com/SaltedTan/virgil-language-server/issues/191#issuecomment-6603166249)). Deep nesting and long operator chains stop at an earlier cutoff than native, bounded by the JVM parser's [stack guard](0017-jvm-parser-stack-guard.md) ([#461](https://github.com/SaltedTan/virgil-language-server/issues/461), [PR #472](https://github.com/SaltedTan/virgil-language-server/pull/472)). A JVM null dereference reports `java.lang.NullPointerException` and exit status 1 rather than native's `!NullCheckException` and status 255, with the worker's containment and restart behavior preserved ([#462](https://github.com/SaltedTan/virgil-language-server/issues/462), [PR #471](https://github.com/SaltedTan/virgil-language-server/pull/471)). On macOS, directory operations fall back to canonical paths and `fileKey` checks, because the platform's directory stream isn't a `SecureDirectoryStream`; a local process can still swap a directory for a symbolic link during an operation ([#473](https://github.com/SaltedTan/virgil-language-server/issues/473), [PR #479](https://github.com/SaltedTan/virgil-language-server/pull/479), [development guide](../development.md#the-jvm-target)). The worker's heap figures come from the JVM, so its restart threshold is approximate ([#463](https://github.com/SaltedTan/virgil-language-server/issues/463)).
6. **The JVM lanes are advisory, and native arm64-darwin is not funded.** CI's JVM jobs for Apple Silicon without Rosetta translation, `test-macos-jvm`, `jvm-package`, and `jvm-archive-macos`, are advisory checks, not required checks on `main`, by the maintainer's 2026-11-08 decision ([#465](https://github.com/SaltedTan/virgil-language-server/issues/465), [PR #484](https://github.com/SaltedTan/virgil-language-server/pull/484), [compatibility](../compatibility.md#host-platforms)). While the JVM build is a preview, the release workflow runs its two JVM editor jobs separately and advisory, so a failed JVM editor job doesn't stop the release, although publication still requires the release's JVM package and archive-test jobs and the runtime's source archive ([#578](https://github.com/SaltedTan/virgil-language-server/pull/578), [release guide](../releasing.md#how-the-workflow-works)). Native `arm64-darwin` remains the long-term target, but it isn't funded now and no native arm64 support is claimed ([#191](https://github.com/SaltedTan/virgil-language-server/issues/191#issuecomment-6602928854)).
7. **Taking this upstream is deferred.** Questions to upstream about a supported JVM host-call interface and about arm64-darwin plans stay on hold until the maintainer approves raising them ([#191](https://github.com/SaltedTan/virgil-language-server/issues/191#issuecomment-6602928854), [#459](https://github.com/SaltedTan/virgil-language-server/issues/459)).

## Consequences

- The default macOS downloads and the supported-platform policy don't change: Apple Silicon stays supported through the Intel build under Rosetta 2, and Linux x86-64 and Intel macOS keep their builds ([compatibility](../compatibility.md#host-platforms)).
- Users on an Apple Silicon Mac without Rosetta 2 install the JVM archive or the `darwin-arm64-jvm` VSIX themselves. Both run without Rosetta 2 or a system Java installation ([release guide](../releasing.md#installing)).
- The JVM build's costs are startup and JIT warm-up, and memory above the native build's. The flags and the 1 GiB envelope bound them without changing the Linux budgets, and the worker's restart after 100 analyses pays a fresh JVM start and warm-up ([#463](https://github.com/SaltedTan/virgil-language-server/issues/463), [JVM memory note](../testing-notes/jvm-memory.md)).
- Native-only assumptions became per-target components: a JVM `HostOs` and runtime bridge, the parser's [stack guard](0017-jvm-parser-stack-guard.md), crash classification, pointer word loads, and worker heap and collection statistics ([#460](https://github.com/SaltedTan/virgil-language-server/issues/460), [#469](https://github.com/SaltedTan/virgil-language-server/pull/469)).
- The signing and notarization position is the same as for the other assets: the launchers and jars are unsigned and nothing is notarized, while the runtime's native files keep Eclipse Adoptium's code signatures ([#464](https://github.com/SaltedTan/virgil-language-server/issues/464#issuecomment-6678602912), [release guide](../releasing.md#the-jvm-build-for-apple-silicon)). A Gatekeeper check on macOS 27.0.1, with network access, accepted the runtime's signed `java` while it killed a quarantined unsigned program in the same test; offline behavior was not tested, and the runtime's binaries had no stapled notarization ticket ([release guide](../releasing.md#installing)).
- If Apple removes Rosetta 2 before a native `arm64-darwin` target exists, the JVM build is the path to keep that Mac supported. Switching it to the default, and any upstream work, are later decisions ([#191](https://github.com/SaltedTan/virgil-language-server/issues/191#issuecomment-6618907630)).
- The Temurin release and the linked runtime are pinned, so a change to either means updating the pinned inventories in the same change ([release guide](../releasing.md#the-jvm-build-for-apple-silicon), [third-party notices](../../THIRD_PARTY_NOTICES.md#eclipse-temurin-java-runtime-jvm-assets-only)).

## Alternatives considered

- **Fund native `arm64-darwin` now.** Upstream has no arm64 Mach-O output, Darwin arm64 system-call or signal stub, `rt/arm64-darwin`, or code signing, and its backend uses a register Darwin reserves. The probe estimated the work as unclear and likely large, and the maintainer chose not to fund it ([#191](https://github.com/SaltedTan/virgil-language-server/issues/191#issuecomment-6601944751)).
- **Make the JVM build the default for `darwin-arm64` now.** On the M4 it started about 154 ms later than Rosetta and sampled about twice the Aeneas memory, while macOS still includes Rosetta 2. The maintainer kept the Intel build as the default and left the switch to a later decision ([#191](https://github.com/SaltedTan/virgil-language-server/issues/191#issuecomment-6603166249), [#464](https://github.com/SaltedTan/virgil-language-server/issues/464)).
- **Require a separately installed Java runtime.** That would add a prerequisite and leave users to choose and update a JDK. The JVM assets bundle a pinned Temurin `java.base` runtime with its notices and source archive instead ([#464](https://github.com/SaltedTan/virgil-language-server/issues/464#issuecomment-6678602912), [PR #482](https://github.com/SaltedTan/virgil-language-server/pull/482)).
- **Use the JVM build everywhere.** [ADR-0003](0003-supported-platforms.md) already rejected it for every user: it adds a Java dependency, slower startup, and more memory. It stays the Apple Silicon fallback, not the general build.
