# 0019. Format Virgil code in its author's style, keeping line breaks

- Status: Proposed; supersedes the roadmap's formatter non-goal
- Date: 2026-11-18
- Discussion: [#504](https://github.com/SaltedTan/virgil-language-server/issues/504)

## Context

The [roadmap](../../ROADMAP.md) previously listed a formatter as a non-goal for the first release ("Formatting is a separate language-design/tooling project"), and its feature table deferred `formatting` to "a future canonical formatter". Virgil has no formatter. Aeneas's `VstPrinter` reprints a syntax tree without its comments, so it can't format source. Editors therefore can't format Virgil: LazyVim's format on save and `<leader>cf` do nothing for `.v3` files, nor does VS Code's Format Document, and this repository's style is enforced only by review.

Ben Titzer's code in Virgil and Wizard engine, about 160,000 lines, has a consistent style that a formatter can follow. Tabs indent 99% of indented lines. `{` ends its line, and `} else {` shares one. A statement is written `if (c)`, and the expression form `if(c, a, b)`. Annotations are `x: T`, and empty bodies `{ }`. There are many one-line braceless `if (...) stmt;` and hand-aligned columns of `=`, `=>`, `//`, and `:`. There is no line limit; with tabs eight columns wide, 99% of lines fit in 130 columns, and the longest has 239. A canonical reprinter, which chooses every line break and wraps long lines, would rewrite most of this code and lose its one-line forms and its alignment.

The server already parses an open document's text without verifying it, for outlines, folding ranges, and selection ranges (`AeneasAdapter.foldingRanges`), under the 350,000-token [parse budget](../architecture.md#document-symbols). Its `SymbolSyntaxIndex` records each token the parser consumes, and after a parse without errors the gaps between those tokens hold only whitespace and comments; the folding collector relies on that.

A spike ran a throwaway prototype over `aeneas/src`, `lib`, `apps`, and `test` of the pinned Virgil (`b86f43f1`), over Wizard engine at `958c6ad5`, and over this repository. The spike note has line-diff totals, counts by edit kind, and sample diffs. [Formatter spike](../testing-notes/formatter-spike.md)

Most of the changes to Titzer's code are whitespace at line ends and at the end of files, and lines indented with spaces, many of them in files from other contributors. The rest bring a line to the form that the code itself uses nearly everywhere: for example, 41 statement `if(` against 13,692 `if (`, and 24 `}` and `else` on separate lines against 1,389 `} else`. Two places in 162,185 lines are judgment calls. Every file that the prototype formatted kept its tokens, and formatting it again changed nothing. The corpora and a review exposed fourteen rule bugs in the prototype, all fixed; the note lists them.

## Decision

1. **The server formats Virgil code in its author's style, keeping line breaks, as `gofmt` does for Go.** It keeps comments, one-line braceless statements, and hand-aligned columns, and normalizes indentation and spacing between tokens. The line-break exceptions in decision 3 are the `} else` and body `{` joins and end-of-file normalization. On 2026-11-18 the maintainer chose the `gofmt` convention of exactly one line end for command-line formatting and left insertion of a missing final line end to the editor for LSP formatting. It doesn't reprint the program, wrap lines, reorder anything, or take style options. This supersedes the roadmap's non-goal.

2. **Only whitespace around tokens and comments changes.** The formatter reads the tokens that the parser consumed and scans each gap once, including before the first token and after the last. It emits one nonoverlapping byte-offset edit for each changed whitespace run, with comments separating runs and an empty range for an insertion. Each token and each comment keeps its bytes, except that trailing whitespace after a line comment is removed. Lines inside a block comment keep theirs, and a block comment left open at the end of the file, which the parser accepts, runs to the end untouched. Line breaks stay where they are except for the two joins and the end-of-file rule in decision 3, which leaves at most one line end after the last token or comment and requires one for command-line formatting where the rule applies. LF and CR LF each count as one line end. Edits preserve retained line ends byte for byte and never split a CR LF pair. The formatter refuses any CR without a following LF before normalizing or parsing the input. The folding parse treats a lone CR as a line end, while the compiler's lexer continues a `//` comment through a lone CR. A file that doesn't parse with its project's language options isn't changed, so a half-typed file is never mangled. A file with more tokens than the parse budget is refused, as an outline is.

3. **The rules.** Each one is the majority form in Titzer's code; the [spike note](../testing-notes/formatter-spike.md#the-counts-behind-each-rule) gives the counts.

   *Indentation*, in tabs:

   - A file-level line has no indentation. A line that starts a statement, a declaration, an enum case, or a match case or one of its patterns gets one tab more than the line where the statement that holds its block started. A `}` line gets that line's indentation. A `{` inside parentheses, such as a `fun` body passed as an argument, anchors its body and closing `}` on the line it occupies after any join. When a match case's `=>` starts its line, the braced body is one tab deeper than the arrow line and the closing `}` aligns with the arrow. The parse tree, not the tokens, says where enum cases start, since their commas are optional.
   - A braceless body on the line after `if (...)`, `while (...)`, `for (...)`, `else`, or a match case's `=>` gets one tab more than its statement's line. A match case's `=>` that starts a line gets one tab more than the start of that case.
   - Any other line is a continuation, including a line that starts with `=>` for a simple method body. It keeps its indentation, including spaces that align it. When its statement's first line is reindented, and that line's old indentation is a prefix of this line's, the prefix is replaced by the first line's new indentation; otherwise this line is left alone. Titzer indents these lines in several ways (one tab 75%, two tabs 11%, aligned under a parenthesis), and a rule that made them uniform would change 1,769 lines of that code.
   - A comment line takes the indentation of the code line after it, or the block's for a comment before `}`. A comment at column 0 stays there: 211 such lines in Titzer's code are section dividers and commented-out code. A comment inside parentheses or brackets follows that list's continuation lines.

   *Spacing* within a line:

   - `if (`, `while (`, `for (`, and `match (` for statements, and `if(` for an `if` expression. Whether an `if` is a statement or an expression comes from the parse tree: tokens alone misread an `if` expression in a `for` header after `;`, or in a `fun` body inside a match case.
   - Remove a single space before a colon after a name and add a space after it if needed, as in `x: T`.
   - At least one space on each side of `=` and the compound assignments, of `->`, including in function types such as `int -> bool`, and of `=>`. A layout's size, such as `=16;`, is not an assignment.
   - At least one space after a comma, unless the line ends there. Spaces before a comma are left alone: 20 of the 23 in Titzer's code align the columns of a table.
   - At least one space before a `{` that follows a token on its line, and before a `//` comment after code.
   - Exactly one space in `if (`, `while (`, `for (`, `match (`, `} else`, `else {`, `else if`, and `{ }`, and none in `if(` for an expression. An empty body `{}` becomes `{ }`.
   - Every other rule only inserts a missing space, or removes the single space before a colon. A gap of a tab or of two or more spaces is alignment and is kept, also before a colon, as in layout fields. Nothing else changes: `Array<int>`, `x.f(y)`, and `#hints` keep their spacing, and so do binary operators.

   *Lines*:

   - Trailing whitespace is removed, and whitespace-only lines become empty, including those before the first token. Blank-line runs before the last token or comment are kept. The line rules apply to LF and CR LF, including files that mix the two.
   - After the last complete token or comment, trim the trailing whitespace. `textDocument/formatting` retains the first line end in that whitespace only if the input ends with a line end. Otherwise it removes the entire whitespace suffix, including any line ends before trailing spaces. For this suffix, every `virgil-lsp format` mode requires exactly one final line end. It keeps the first one if present, or adds one of the kind used first in the file, defaulting to LF. A whitespace-only file becomes empty. If the file ends inside a block comment, the comment runs to EOF untouched and no line end is added.
   - `else` after a `}` that starts its line joins it as `} else`. After a one-line block, `if (c) { ... }`, an `else` on the next line stays.
   - A body's `{` on a line of its own joins the line before, which ends a header. A `{` after `;`, `{`, or `}` starts a block statement and stays. Compute indentation from the lines after the joins. For a body indented from its opening `{`, the joined header line anchors both the body and the closing `}`, just as if the brace had already been on that line.
   - Both joins apply only across exactly one line end with nothing but whitespace around it: never across a blank line or a comment.
   - Keep an empty body's braces on separate lines when they already are. This occurs in 61 places in Titzer's code, mostly after long class or constructor headers.

4. **The formatter lives in `src/analysis/`, beside the folding collector.** `DocumentFormatter` walks the input's tokens and the gaps between them. The parse tree tells it each `if` keyword's kind, where enum cases start, and which `=>` tokens delimit match cases. It computes the formatted byte size before building replacement text, so callers can enforce their output limits before allocating edits. It produces byte-offset edits of a server-owned type for callers that need them. `AeneasAdapter.formatting(path, input, options)` checks the original bytes for a lone CR. For admitted input it parses the current text with the project's language options under the parse budget, as `foldingRanges` does. It reports a lone CR, the first parse error, or a parse-budget refusal. No Aeneas type leaves `src/analysis/` ([ADR-0002](0002-pinned-virgil-adapter-boundary.md)).

5. **The server answers `textDocument/formatting`.** It formats the open document's current text and returns the edits from decision 2 as LSP ranges in document order. Each edit covers one changed whitespace run, keeping tokens and comments out of the replacement ranges so editors can preserve cursors, marks, and folds there. If there are more than 10,000 edits, the server returns one merged edit from the first change to the last, including any intervening comments with their original bytes.

   - The server marks every open document on a connection out of sync only when the transport skips a frame or the JSON-RPC decoder cannot decode a payload, for example because the JSON is malformed or exceeds the value limit. It marks them before handling the next message because it may have missed a document change whose URI it cannot determine. A rejected change with a known URI marks only the identified open document. This includes a document store over capacity, an unsupported incremental change, or invalid change parameters. A valid ignored notification such as `$/setTrace` leaves synchronization unchanged. Formatting an out-of-sync Virgil document returns `RequestFailed` before parsing, saying the server's copy is out of date. Each document's mark clears when it gets an accepted full-text change or is closed and successfully reopened. A version-only change (empty `contentChanges`) keeps the mark because it cannot restore the text. The maintainer chose these rules on 2026-11-18.
   - When trimming whitespace after a complete token or comment, the request retains one final line end only if the input ends with one. Otherwise it removes the entire suffix, so Neovim's `fixeol` or VS Code's `files.insertFinalNewline` can add the final line end on save. The request empties whitespace-only text and preserves the end of an open block comment. See decision 3.
   - Indentation can make a document grow: a small file of deeply nested empty statements can grow past 1 MiB. The server uses the formatted size from decision 4 to refuse with `RequestFailed` if the document store, whose 1 MiB budget covers every open document and its metadata, couldn't accept the formatted text in place of the current one. It also refuses a reply whose JSON would exceed 4 MiB, the bound that document symbols use.
   - The request's `FormattingOptions` must include `tabSize` as an unsigned integer (`uinteger` in LSP 3.17) and `insertSpaces` as a boolean. A missing or wrongly typed member gets `InvalidParams`. The formatter uses its tab indentation rules regardless of these values.
   - A document with a lone CR gets no edits and no error, as does a document that doesn't parse. Format on save of a half-typed file shouldn't interrupt with an error, and its diagnostics already show the syntax error. A document over the parse budget gets `RequestFailed`, as an outline does. A document that isn't Virgil, such as a project file, gets no edits.

   The server registers formatting dynamically for documents of the `virgil` language when the client supports `textDocument.formatting.dynamicRegistration`, as VS Code and Neovim do, so that VS Code doesn't offer it as a second formatter for `.virgil-lsp.json`. Otherwise it advertises `documentFormattingProvider` statically. Range formatting isn't offered. As [CONTRIBUTING](../../CONTRIBUTING.md#pull-requests) requires, the capability is advertised only by the change that implements and tests it.

6. **The same code formats files from the command line.** On 2026-11-18 the maintainer chose to offer standard-output mode for scripts and tests that need the formatted bytes, and `--write` so contributors can fix a failed check without an editor. The command is `virgil-lsp format [--check | --write] [-lang:<option>...] <file.v3>...`.

   - If the platform layer cannot provide the required metadata from an open file descriptor, as with the current JVM bridge, `--write` reports the platform by name and exits with 1 before opening any input or creating a temporary file. On the JVM, `--check` and standard-output mode use the existing bridge. It checks that the path resolves to a regular file before opening a blocking channel. If a FIFO replaces the regular file between the check and the open, either mode can wait for a writer.
   - On native builds, every mode uses a nonblocking input open and checks that the opened descriptor is a regular file before reading. In every supported mode, the command reports and refuses inputs detected as nonregular. It reads each admitted file with a byte limit before parsing, as the server does for project sources, and refuses a file that exceeds the input limit. `--write` opens the named input for reading and writing without truncating it or following a symbolic link. If the caller cannot open the input for writing, the command reports the file and leaves it unchanged. Immediately after opening, it records the device, inode, size, modification time, status-change time (`ctime`), owner, group, and permission bits from the descriptor. It compares them with the named path's metadata without following a symbolic link and checks that the opened file and named path have no ACL or other extended attributes. It refuses a mismatch or unsupported attribute before reading any bytes and uses the descriptor's snapshot for both later checks. It reports a symbolic-link input before opening its target and leaves both the link and its target unchanged. `--check` and standard-output mode open files for reading and follow symbolic links.
   - In every mode, the command checks each file's formatted byte size against a fixed output limit before building replacement text or formatted output. If the size exceeds the limit, it reports the failure for that file as it does for a syntax error.
   - With neither flag, it accepts one file and prints the formatted bytes to standard output.
   - `--check` finds the first changed line without building replacement text or formatted output. It names each file that would change, with that line, and prints nothing for a formatted file.
   - For a file whose text changes, `--write` creates a temporary file in the same directory with read and write access for its owner alone. Before writing the formatted bytes, it checks that the temporary file has the same owner as the original and has no inherited ACL or other extended attributes. After writing, it rechecks the named path against the input descriptor snapshot without following a symbolic link. It then sets the original's owning group and permission bits on the temporary file through its descriptor, in that order, and repeats the check immediately before the atomic rename. Both checks compare the recorded device, inode, size, modification time, `ctime`, owner, group, and permission bits, and confirm the path still has no ACL or other extended attributes. Before renaming or removing the temporary entry, it looks up the temporary name without following symbolic links and verifies that its device and inode match the retained temporary descriptor. If the temporary name cannot be verified, it reports the input path and leaves both names alone. For other failures, it reports the input path, leaves it alone, and removes its temporary entry only after verifying its identity at cleanup. The command takes no lock. A concurrent change can race with setting the temporary file's permissions, and a save, metadata change, or entry substitution after the final checks can still race with rename or cleanup.
   - In every mode, the command reports a file with a lone CR and leaves it unformatted. It exits with 0 on success and with 2 for invalid arguments. It exits with 1 if any file would change under `--check`, can't be formatted (nonregular, unreadable, with a lone CR or syntax error, or over the input, parse, or output limit), or is refused or fails replacement under `--write`, including denied write access or a change detected before rename.
   - It accepts the language options that a project file's `compilerArgs` accepts, with the same rules for values and repetition.

   `make check-format` runs `--check` on this repository's tracked `.v3` files, except `vendor/`, `test/fixtures/`, the editor tests' fixtures under `test/e2e/`, and `docs/examples/`, whose bytes and positions tests depend on. `make test` runs it as a suite, so CI fails on unformatted code.

7. **Editors format through the server.** LazyVim needs no change: its default autoformat formats `.v3` files on save through the language server, and `<leader>cf` formats on demand. Plain Neovim formats on demand with `vim.lsp.buf.format()`, and Helix's `:format` uses the server too. VS Code supports Format Document. Its extension contributes `"[virgil]": { "editor.formatOnSave": true, "editor.insertSpaces": false, "files.insertFinalNewline": true }` as configuration defaults, which users can override. An explicit save requests formatting. VS Code's format-on-save participant skips delayed auto saves (`files.autoSave: afterDelay`). VS Code adds a missing final newline on save through `files.insertFinalNewline`. The maintainer chose these defaults on 2026-11-18.

   In plain Neovim and LazyVim, a buffer read from a file without a final line end can be left with an empty last line. The separator before that empty line is the last thing in the text sent to the server, where it is indistinguishable from a final line end. With `fixeol`, the save writes one extra blank line. Formatting again after reloading the file removes that blank line.

## Consequences

- LazyVim formats on save with no setup. VS Code formats on explicit saves by default and skips delayed auto saves (`files.autoSave: afterDelay`). A team with another style turns off format on save, since the formatter has no options.
- Titzer's code isn't format-clean: formatting the pinned Virgil sources would change 0.6–1.5% of their lines, and Wizard engine 1.6%. The corpus record makes each of those changes visible, and a pin update shows how they move.
- The formatter's output is part of the server's behavior. A rule change that formats existing code differently is a user-visible change, recorded in the changelog.
- Each request costs one parse of the document, as folding ranges do, and a linear pass over its tokens.
- The formatting request returns no edits or error for a file with a lone CR or a syntax error. VS Code can still add a missing final newline on save through `files.insertFinalNewline`. A file whose formatted text wouldn't fit in the document store is refused with a message.
- Code actions and rename can currently return edits against an out-of-date copy. The follow-up applies the same synchronization rules to them after a rejected change to an identified document, a skipped frame, or an undecodable payload. It also tracks rejected opens with a known URI at the document synchronization boundary. Rename checks every document it would edit and refuses if any target is known to be out of sync. If a skipped frame or an undecodable payload contained a `didOpen`, the server cannot identify its URI. A rename based on disk text could then return edits for a dirty buffer. The follow-up will decide whether and how to guard those targets. [#514](https://github.com/SaltedTan/virgil-language-server/issues/514)
- The native platform layers in `src/os/` (`x86-64-linux` and `x86-64-darwin`) supply the nonblocking opens and descriptor type checks in decision 6. For `--write` they also supply atomic rename, no-follow metadata lookups for the input and temporary names, and ways to read access metadata by descriptor and by path without following links. They create temporary files with owner-only access and set their group and permission bits. The JVM modes in decision 6 require no new JVM host support. [#508](https://github.com/SaltedTan/virgil-language-server/issues/508)
- This repository's sources need 35 lines changed once, mostly `{ if(c) stmt; }` in one-line blocks.
- Pin updates gain a step: regenerate and review the corpus record. The [pin update steps](../../CONTRIBUTING.md#updating-the-pinned-virgil-revision) will name it.
- The work is split into issues under [#504](https://github.com/SaltedTan/virgil-language-server/issues/504): the formatter's indentation and line rules, its spacing rules, the command, its `--write`, the corpus check, this repository's check, the LSP request, and the editors.

## Alternatives considered

- **Reprint from the syntax tree, as `VstPrinter` does.** It drops comments, and a canonical reprint discards the author's line breaks, one-line forms, and alignment.
- **A canonical formatter with a line limit, as `rustfmt` or Prettier do.** Titzer's code has no line limit and relies on hand alignment; such a formatter would rewrite most of it.
- **Indent every continuation line one tab more than its statement.** That would change 1,769 lines of Titzer's code, which aligns these lines in several ways.
- **Indent comments at column 0 like the code after them.** That would move 211 section dividers and commented-out lines in Titzer's code.
- **Tell an `if` expression from its tokens.** A comma in its parentheses misreads type arguments, as in `if (eq<T, int>())`, 130 times in `vendor/virgil/test`, and a statement-start rule over tokens misreads `for` headers and `fun` bodies inside match cases. The parser already decides.
- **Remove spaces before commas.** Twenty of the 23 in Titzer's code align a table's columns.
- **A separate formatter, outside the server.** It would need its own parser; the server already parses current text with recovery and a budget, and one formatter serves the editors and the check.
- **Replace the whole document.** Edits confined to changed whitespace runs let editors preserve cursors, marks, and folds in the surrounding text.
- **Answer a document with syntax errors with an error.** Format on save would interrupt saves of half-typed files with an error.
- **Follow `FormattingOptions.insertSpaces`.** The result would depend on each editor's settings, and Virgil code is indented with tabs.
- **Leave VS Code's format on save to each user.** LazyVim formats on save by default; the maintainer chose the same for VS Code.
