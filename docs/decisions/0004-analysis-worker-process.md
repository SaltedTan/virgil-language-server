# 0004. Run whole-program analysis in a replaceable worker process

- Status: Accepted
- Date: 2026-10-03
- Discussion: [#13](https://github.com/SaltedTan/virgil-language-server/issues/13)

## Context

The compiler spike ([#1](https://github.com/SaltedTan/virgil-language-server/issues/1), [PR #11](https://github.com/SaltedTan/virgil-language-server/pull/11)) found that whole-program analysis (`Compilation.parse()` and `verify()`) cannot run safely in the language server's process:

- **Ordinary input can kill or hang the process.** Virgil has no exception handling, so a trap inside Aeneas ends the process. `def x: i32 = 0i;` (typed on the way to `0i32`) and `enum E { A(6) }` trap with `!NullCheckException`; `class S extends S { def f() { me; } }` loops forever. [Aeneas crash paths](../aeneas-crash-paths.md) lists the known inputs.
- **Analyses leave process-wide state behind.** `UID.next` never resets, and verification of any program fails once it passes 2^29, which is about 16,500 analyses of the Aeneas sources. [#12](https://github.com/SaltedTan/virgil-language-server/issues/12) removed the type-cache retention that made the second such analysis run out of heap, but the adapter cannot reset the compiler in general.

Two properties of the Virgil runtime shape the answer:

- `System` has no way to create a process, so this needs raw system calls through `Linux.syscall` and `Darwin.syscall`.
- The heap size is fixed when an executable is compiled (`-heap-size`, 200 MB by default in `bin/v3c-*`). The semispace collector allocates through its whole from-space before each collection, so a busy process's resident memory approaches the configured heap.

## Decision

### Processes

1. **Two executables from the same sources.** `virgil-lsp` is the server. `virgil-lsp-worker` runs analyses and nothing else. Its entry point is `src/worker/WorkerMain.v3`, and it is compiled with its own heap (`WORKER_HEAP` in the `Makefile`, 384 MB; see [Measurements](#measurements)). The server keeps the default heap.
2. **The server never parses or verifies a whole program.** Of the two product executables, only the worker calls `AeneasAdapter.analyzeProgram`; adapter tests and probes still call it directly. See [Compiler adapter](../architecture.md#compiler-adapter) for the shared parser and verification driver. This supersedes the in-process whole-program analysis portion of [ADR-0001](0001-virgil-native-server.md), retaining its choice of Virgil and the compiler's semantics. Virgil compiles only reachable code, so the verifier isn't even in the server executable (before stdio integration: 306 KB, against 607 KB for the worker, on Linux). Single-file parsing (`parseFile`, document symbols) stays in the server and has its own, smaller set of [known crash paths](../aeneas-crash-paths.md). Keeping it in-process allows syntax diagnostics independently of worker availability.
3. **Starting a worker.** The server looks for `virgil-lsp-worker` in its own executable's directory. On Linux it reads `/proc/self/exe`; on macOS it calls `proc_info` with `PROC_PIDPATHINFO`, as `proc_pidpath()` does. `src/os/<target>/HostOs.v3` holds the system calls for each target, and the `Makefile` compiles the one for the host. The server creates two pipes and moves their descriptors to 10 and above, close-on-exec. It then forks and `execve`s the worker with the argument `--serve` and an empty environment. In the child, descriptor 0 is `/dev/null`, descriptors 1 and 2 are the server's standard error, and descriptors 3 and 4 carry requests and results. A worker can therefore never write to the server's standard output, which belongs to the protocol. The server checks that the file is executable before forking; a child that still cannot `execve` exits with status 127. The supervising process ignores `SIGPIPE`, so that writing to a dead worker fails with `EPIPE` instead of killing it.
4. **Handshake.** A worker starts by sending its protocol version, server version, source revision, and heap size. The server refuses a worker whose version or revision differs from its own (a stale or mismatched executable) and reports why.

### Channel and framing

Requests and results each use one pipe. A frame is a 4-byte little-endian payload length followed by the payload, at most 16 MiB (`WorkerFraming.MAX_PAYLOAD`). The first payload byte gives the message kind. Unless noted, integers are signed LEB128, and strings are a length (-1 for null) followed by the bytes. `RESULT` starts with fixed-width request ID, analysis count, and UID counter (32 bits each), then live heap bytes (64 bits), all little-endian. Its flags and declaration-kind tags are single bytes. `src/worker/AnalysisWire.v3` holds the encoder and decoder for both directions. Released layouts require an `AnalysisWire.PROTOCOL_VERSION` change; version 4 remained unreleased, so the type-parameter declaration kind and skipped-uses statistic were added without another version change. Version 5 adds [display text](../architecture.md#display-text) for hover: a string table that also holds declaration names, a signature per declaration, use-site types, builtin uses, and declaration sites. It also drops the path table: a path is an index into the request's paths. Version 6 adds the `PACKING` declaration kind ([#111](https://github.com/SaltedTan/virgil-language-server/issues/111)) after the others, so every earlier kind keeps its tag; the layout is unchanged. Version 7 adds [call sites](../architecture.md#call-sites) for signature help ([#126](https://github.com/SaltedTan/virgil-language-server/issues/126)): call signatures after the declarations, and each file's calls after its builtin uses. Version 8 adds the scope query of [completion](../architecture.md#completion) ([#129](https://github.com/SaltedTan/virgil-language-server/issues/129)): an `ANALYZE` flag, `WANT_SCOPE`, with the query after the files, and a `RESULT` flag with the answer after the occurrence section. A request without the flag, and its result, are the same bytes as in version 7.

| Message | Direction | Contents |
| --- | --- | --- |
| `HELLO` | worker → server | Protocol version, server version, source revision, heap bytes |
| `ANALYZE` | server → worker | Request ID, flags (collect occurrences, collect statistics, answer a scope query), the server's time limit, the program's [language options](../configuration.md#compiler-flags) in the order given, then each file's path and bytes, in program order; with `WANT_SCOPE`, the scope query: a file's index in the request, a byte offset in it, the kinds of names (values, types, a pattern's heads, the layouts that `Ref<...>` takes), or members alone for a member query, or the call alone for a call query, and the identifier's prefix, at most 255 bytes, which a call query leaves empty |
| `RESULT` | worker → server | Request ID, and the worker's analysis count, UID counter, and live heap; parse/verify flags and statistics, including the [skipped-use total](../architecture.md#compiler-adapter); diagnostics; with occurrences, a string table, each distinct declaration once, the call signatures, and each file's index (below); with a scope, member, or call query, its answer (below). Diagnostic and declaration ranges hold compiler coordinates and UTF-8 byte offsets. An occurrence is a single-line token whose compiler column span equals its byte length, so it is sent as its begin line, column, and offset and that length |

A `RESULT`'s occurrence section, since protocol version 7, with version 11's write bit, version 12's resolved-type targets, version 13's inlay hints and compact coordinates, and version 14's parents:

A path is an index into the distinct path strings of the `ANALYZE` request, in order of first appearance. The request still sends every source, so a repeated path takes the index of its first copy. Every declaration is in one of the request's files, so the result needs no path table, and the decoder never looks a path up by text.

1. The string table: a count, then each distinct string once, never null. Declaration names, signatures, use-site types, and builtin types are indexes into it, so text that many declarations or uses share, such as a common type, crosses once.
2. The declarations: a count, then for each its kind tag (one byte), its name's string index, its path index, its range (four compiler coordinates and two byte offsets), its signature's string index plus one, or zero for none, its default resolved-type target (declaration ID plus one, or zero for null) since version 12, and its parent in the class and override hierarchy (declaration ID plus one, or zero for none) since version 14. The encoder sends only parents that are among the declarations it sends.
3. The call signatures that the calls use, each once, the most used first: the signature text, a count and then the strings that signatures use and the string table lacks, such as most parameter labels; then a count and, for each signature, its label, the byte in the label where its first parameter starts, and a count and its parameters' labels. A label is a string table index or, past the end of the table, a signature text index.
4. The files: a count, then for each:
   - its path index, and the index and count of its declaration sites, a run of the declarations that are in the file, in byte order without overlaps. The encoder puts each file's sites first, in file order, so that they are a run;
   - its occurrences: a count, then for each its begin line, column, and offset, its length, and its declaration index (complemented for an assignment target since version 11). Since version 13, a negative count selects compact storage for its absolute count of occurrences: line and column share one integer when both fit 16 bits, saving one array element per occurrence. Full-width fallback preserves larger coordinates; both forms still send and validate all four range integers;
   - its use-site types: a count, then for each the difference between its occurrence index and the previous one's (the first's from zero), so that they strictly increase, and a string index. An occurrence without one costs nothing;
   - its builtin uses: a count, then for each a range as an occurrence's, and its type's string index;
   - its resolved-type overrides, since version 12: a count, then byte-offset delta and target-code pairs (declaration ID plus one, or zero for explicit null), differing from the default stored with each declaration; every 32nd offset is absolute, all offsets strictly increase, and each begins an indexed name. Defaults are shared only for storage; each recorded name is compared with its default, including names whose type has no source location. The decoder retains the encoded pairs and charges their bytes and a checkpoint pair per block against the result budget. See [Type definition](../architecture.md#type-definition) for default selection, ordered validation, and retained snapshot storage;
   - its calls, in the order of their opening parentheses: a count, then for each, in unsigned LEB128, its opening parenthesis as the difference from the previous call's (the first's from zero); its head, its argument count times eight plus three flags; with the second flag, its callee's offset before the parenthesis; its signature's index plus one, or zero for none; for each argument, its length times four plus the bytes between it and the previous argument's end (the first's from just after the parenthesis), or three, and then those bytes; and, with the third flag, the bytes between its last argument and its closing parenthesis. The first flag alone makes the callee the use that ends at the parenthesis. Since version 13, the first and second flags together mark parameter labels: the explicit callee delta is zero when absent, and every argument carries a label string ID plus one (zero when suppressed), reusing its existing span. Query-only call answers omit labels. The 5.4-byte average for Aeneas calls was measured before version 13.

Version 13 adds each file’s local hint count and compact records after its calls. Each record holds a begin-offset delta, span length, local declaration ID plus one, and type-label string ID, all signed LEB128. Parameter labels remain in the call records; no parameter span repeats. The decoder bounds counts by available bytes, requires positive nonoverflowing spans in strictly increasing order, validates string references, and requires each local hint to match a local declaration site in the same file with exactly its span. Strict UTF-8 decoding rejects invalid, overlong, surrogate, and out-of-range sequences; labels must be nonempty and contain no ASCII control characters. Type labels additionally exclude `?` and are bounded to 40 code points. Each distinct string is checked once per hint kind, while span and declaration checks run for every record. The retained local-hint array costs 64 bytes plus its encoded byte length when nonempty; argument labels are included in the existing call-array byte charge. The result budget is unchanged ([Inlay hints](../architecture.md#inlay-hints)).

The decoder rejects a string index out of the table or of a null entry, an occurrence index out of the file's occurrences or not increasing, and sites that are out of the declarations, in another file, empty, unordered, or overlapping. It rejects a parent out of the declarations or the declaration itself, and any parent except a class or variant case for a class, a class for a variant case, and a method for a method; parents may not form a cycle, which the encoder never sends: it drops the parents on an inheritance cycle, which verification reports ([implementation](../architecture.md#implementation)). It rejects a signature whose label or parameter is not a string, whose first parameter would start past the end of its label, or whose parameters, laid out from there with their separators, would end past `int.max`, and a call whose opening parenthesis is not after the previous call's, whose argument list is not inside that of each call it starts in, whose callee is not one of the file's occurrences or builtin uses, or whose signature index is past the signatures, as well as an empty argument and an offset past `int.max`. Occurrences and builtin uses must each be in byte order without overlaps, as the snapshot's binary searches require: a positive line and column, a nonnegative offset at or after the previous use's end, a positive length, and an end offset and column that do not overflow. A builtin use must not overlap an occurrence. A file must be one of the request's, named at most once, which bounds the file count by the request, and its site run must start at or after the end of the previous file's, so that the decoder checks each declaration as a site at most once. Each file is marked when it is decoded, by index. Since version 13, callee validation walks the ordered occurrence and builtin spans, retaining binary lookup only for backward targets; each callee must still match the same token endpoint. Decoding the occurrence section is therefore linear in its size apart from those backward lookups, plus sorting the request’s paths once by their bytes and dropping repeats (`AnalysisSnapshotFiles`), so that the snapshot finds a file by its path with a binary search rather than by hashing. Virgil's `HashMap` stops growing at 1,024 buckets and chains paths with equal hashes, so a map from the paths of a large request took time quadratic in their count: decoding a result for 16,000 request paths took 223 ms, and 1,077 ms when their hashes were equal, but takes about 6 ms either way with the sorted index.

A `RESULT`'s scope section, since protocol version 8, follows the files when the request had `WANT_SCOPE`, the program parsed, and verification reached the offset ([Completion](../architecture.md#names)): a flags byte, whose one flag says that the candidates were truncated; the level of `this`, or -1 where no method's receiver is in scope; and a count, at most 1,000, then each candidate's declaration index and level, nearest first; then a count and the strings of builtin names hidden by nearer bindings, even when those bindings are not candidates. The candidates' declarations join the declaration table after the occurrences'. A request with `WANT_SCOPE` but without `WANT_OCCURRENCES` gets an occurrence section with no files, so that its declaration table holds only the candidates, with their signatures, and the result is small; the worker collects no occurrences for it. The decoder rejects a scope section that the request did not ask for or that comes without an occurrence section, an unknown flag, a `this` level below -1, a count past the cap or past the bytes that remain, an index out of the declarations, a declaration named twice, levels that decrease, and null, empty, or repeated hidden names. The hidden-name count is bounded by the same cap and the bytes that remain. It charges 64 bytes for each of the two counts, 8 for each candidate or hidden-name slot, and 64 plus the byte length for each hidden name, against the [result budget](#supported-program-size). The worker validates the query in turn: a request whose query names a file it lacks, an offset outside that file, an unknown kind, or a longer prefix is malformed.

Protocol version 9 adds the member query ([Member completion](../architecture.md#member-completion)). Its request is a scope query whose kinds are `MEMBERS` alone; a request with `MEMBERS` and any other kind is malformed. Its answer gets a `RESULT` flag of its own, `MEMBERS`, and a member section in place of the scope section, with these fields:

- a flags byte, whose one flag says that the candidates were truncated;
- a count, at most 1,000;
- for each candidate, its declaration index plus one, or zero for a builtin member; a builtin member's zero is followed by its kind and its name's string-table index;
- its detail's string-table index plus one, or zero for a declaration's own signature;
- its level.

The candidates' declarations join the declaration table, and the builtin members' names and every detail join the string table. The decoder rejects these answers:

- one that the request didn't ask for, a member section with a scope request, or a scope section with a member request;
- one without an occurrence section;
- an unknown flag, or a count past the cap or past the bytes that remain;
- an index out of the declarations, an invalid string index, or an empty builtin name;
- a kind that no member has: only fields, methods, constructors, classes (for an enum's `set`), cases, and layout fields are valid;
- levels that decrease, or a declaration or a name offered twice, since a member hides others of its name.

Duplicate validation sorts declaration indices and names, taking n log n work in the candidate count. It charges 64 bytes for the count and 32 for each candidate's five slots. A builtin member's name and detail are charged as strings of the string table.

Protocol version 10 adds the call query of signature help ([Incomplete calls](../architecture.md#incomplete-calls), [#163](https://github.com/SaltedTan/virgil-language-server/issues/163)). Its request is a scope query whose kinds are `CALL` alone, with an empty prefix; a request with `CALL` and any other kind, or with a prefix, is malformed. Its answer gets a `RESULT` flag of its own, `CALL`, and a call section in place of the scope section. The worker sends it only where an application's argument list opens at the offset and verification reached it, and only if its record passes the checks that a file's calls pass (`AnalysisCallCheck`). The section has these fields:

- the call, encoded as a file's first call is ([call sites](../architecture.md#call-sites)): its opening parenthesis, as an absolute offset; its argument count times eight plus its flags; the callee's offset before the `(`, with `CALLEE_OFFSET`, since the answer has no uses for `CALLEE_AT_PAREN` to name; its signature's index plus one, or zero; each argument's length and gap; and the closing gap, with `CLOSE_GAP`;
- its callee's declaration index plus one, or zero.

The callee's declaration joins the declaration table, and the call's signature the call signatures, as a file's call's would. Without `WANT_OCCURRENCES`, the occurrence section has no files, so the result holds only that declaration and that signature. The decoder rejects these answers:

- one that the request didn't ask for, a call section with a scope or member request, or one without an occurrence section;
- a callee that ends at the parenthesis, which would name a use, both callee flags, or a callee offset of zero or before the file;
- a signature index past the signatures, an empty argument, an argument count past the bytes that remain, or an offset past `int.max`;
- a declaration index out of the declarations, or trailing bytes.

It charges 64 bytes for the call and 8 for each argument, and, for its signature, 64 bytes, 8 for each parameter, and 64 plus the byte length of each string of signature text that the signature names, which decoding copies.

The server's pipe ends are nonblocking. The stdio event loop polls standard input and the worker pipes together, using the startup or analysis deadline as its poll timeout. Startup, including the handshake, and request transmission are asynchronous too. It therefore never waits on a worker that has stopped reading or writing. The decoder bounds every count by the bytes that remain in the message, and every index by its table. A malformed message is rejected without trapping, and the worker that sent it is killed.

### What crosses the boundary

Requests carry source bytes that the server has read: open-document overlays, or files from disk. The worker never reads a file. Results carry only server-owned snapshot data: diagnostics, declaration and occurrence indexes, and measurements. No `Program`, syntax tree, or other compiler object leaves the worker. The server decodes a result into an `AnalysisSnapshot` (`src/analysis/AnalysisSnapshot.v3`), which keeps occurrences as int arrays rather than an object per use. A snapshot answers `occurrences(path)` and `definitionAt(path, line, column)` the way `ProgramAnalysis` does, and `definitionAtOffset(path, offset)` by byte offset, and stays valid after its worker has exited. Protocol version 5 added the [display text](../architecture.md#display-text) that hover needs ([#105](https://github.com/SaltedTan/virgil-language-server/issues/105)), which the snapshot answers by byte offset too, and version 7 the [call sites](../architecture.md#call-sites) that signature help needs ([#126](https://github.com/SaltedTan/virgil-language-server/issues/126)). Version 8 adds the answer to a completion's scope query ([#129](https://github.com/SaltedTan/virgil-language-server/issues/129)), which crosses only when a request asks for it, as indices into the result's declarations: the worker finds the names visible at the cursor in its syntax tree, and only declarations cross, never the scopes themselves. Version 10 adds the answer to signature help's call query in the same way: the one call whose `(` is at the cursor, in the encoding of a file's calls, never the syntax tree around it. Version 11 adds each occurrence's assignment flag for [document highlights](../architecture.md#document-highlights), packed in the existing target integer after decoding, with unchanged snapshot allocation. The snapshot keeps the calls and their signatures in their wire encoding and makes objects only for the calls a query returns: a query decodes each signature at most once, however many of its calls name it, and copies each string of signature text at most once, however often its signatures name it (`AnalysisSignatureReader`), so that what it allocates is bounded by the calls it returns and the sizes of the distinct signatures they use. Any other data the server needs later will join `RESULT` with a protocol version change when the feature that uses it lands.

### Restart policy

Analyses run one at a time. A worker starts on demand, before an analysis, and is replaced (killed with `SIGKILL` and reaped) when any of these happens:

| Trigger | Limit (`AnalysisWorkerLimits`) | Outcome of that analysis |
| --- | --- | --- |
| It exits, traps, or closes its result pipe during an analysis | — | Failed: crashed |
| An analysis runs past the wall-clock limit, or a start sends no handshake in time | 10 s each | Failed: timed out, or unavailable for a start |
| It sends a malformed result payload | — | Failed: malformed |
| Its result exceeds the decoded allocation budget | 16 MiB (`AnalysisWire.MAX_RESULT_ALLOCATION`) | Failed: too large; reduce the program's source set |
| After a completed analysis, its analysis count reaches the limit | 100 | Completed |
| After a completed analysis, its UID counter reaches the limit | 2^28 | Completed |
| After a completed analysis, its live heap (after a forced collection, excluding the result) reaches the limit | ⅛ of its heap (48 MB) | Completed |

Cancellation withdraws a temporary job's consumer without adding a restart
trigger. The [#262 typing-burst experiment](../benchmarks.md#reclaiming-obsolete-jobs)
tested replacing obsolete temporary work whenever useful work was ready.
Although the last reply's median improved slightly, diagnostics after the burst
arrived later, so that policy was not adopted. The running worker still finishes
and its withdrawn result is discarded; automatic analyses keep their contexts
and snapshot waiters.

Each worker also arms a timer (`setitimer`) for twice the time limit plus a second while it analyzes, and `SIGALRM` ends it. The server's limit normally expires first. The timer matters when the supervising process dies during an analysis: an idle orphan reads the end of its request pipe and exits, but one caught in a compiler loop would otherwise run forever.

Before allocating the encoded request, the supervisor measures its aggregate size with `AnalysisWire.analyzeFrameSize`: framing, message metadata, file counts, path lengths and bytes, and source lengths and bytes. If the payload would exceed the frame limit, it returns `TOO_LARGE` without starting or replacing a worker, sending bytes, or changing the current snapshot. The existing worker can handle the next accepted request. `AnalysisSupervisor:request_too_large`, `AnalysisSupervisor:request_size_boundary`, `AnalysisSupervisor:aggregate_request_too_large`, and `AnalysisSupervisor:oversized_request_keeps_snapshot` cover this admission rule.

If no worker can be started, the analysis fails as unavailable, and the next analysis tries again. Worker startup and execution failures are logged to standard error as warnings, with the process ID and exit status when available. Invalid frame lengths or truncated frames close the result stream and are reported as crashes; malformed result payloads are reported as malformed. Exceeding the decoded allocation budget is instead reported as `TOO_LARGE`, with the budget in bytes and advice to reduce the program's source set. Decoding stops before the allocation that would exceed the budget, so the remaining payload and restart-policy state are not validated. The supervisor conservatively replaces that worker too, without calling its result malformed; replacement does not make the same oversized program fit. `AnalysisSupervisor:over_budget_result_keeps_snapshot` and `AnalysisSupervisor:malformed_result_replaces_worker` cover the distinct outcomes, snapshot preservation, and replacement. Routine replacements get an informational line. A failure never stops the supervising process. The most recent snapshot remains available for inspection, subject to the [snapshot freshness policy](../architecture.md#analysis-snapshots-partly-present), and the next analysis after a worker failure runs in a new worker. The worker inherits standard error, so its trap message and stack trace appear in the server's log.

The UID limit leaves 2^28 IDs of headroom, while one analysis of the Aeneas sources uses 32,462. The count limit is a backstop against growth that the live-heap check cannot see, such as the UID counter itself; replacing a worker costs well under a millisecond. The live-heap limit catches a retention leak long before it can overflow the heap: without #12's cleanup, one analysis of the Aeneas sources retained about 70 MB.

### First clients

`virgil-lsp analyze` and the stdio server share the supervisor state machine. The CLI drives it synchronously; stdio calls `begin`, adds `pollFds` to its stdin poll set, uses `pollTimeout` for the wait, and calls `onPoll` for progress or completion. No worker is started until an analysis is submitted.

Automatic [semantic diagnostics](../architecture.md#semantic-diagnostics) submit analyses of configured projects; they wait while the supervisor is busy instead of being rejected, and their debounce interval also bounds the poll wait. A [rename](../architecture.md#rename) checks its edits with a preflight, which the same scheduler runs in turn with them: an ordinary `ANALYZE`, with occurrences and the program's language options, of the snapshot's exact analyzed sources with the edits applied. The server compares the result's bindings with the snapshot that it planned the edits from. A [completion](../architecture.md#completion) that needs the names in scope runs the same way, as a temporary job of that scheduler: an `ANALYZE` with a scope query and without occurrences, of the project's captured sources with the document's text as typed or repaired at the cursor.

The preflight reuses `ANALYZE` rather than adding a request or an `ANALYZE` variant, as [#125](https://github.com/SaltedTan/virgil-language-server/issues/125) first proposed, so the preflight required no protocol version change. The server already holds the original bindings, in its snapshot, so it can compare two analyses itself, and the worker does nothing it does not already do. The decoder's result budget and the snapshot budget's admission already allow for a second snapshot beside the current one, which an automatic analysis has while it replaces a context's snapshot. `AnalysisSupervisor.beginTemporary` keeps the preflight's result from becoming the supervisor's latest snapshot, which admission never evicts and `virgil-lsp/snapshot` reports, and the server drops the result once compared. On the Aeneas sources, the server's heap holds 24.2 MB after a forced collection while both snapshots are live, as while an automatic analysis replaces a context's snapshot (24.17 MB), and 14.8 MB with one; each snapshot is charged 13.3 MB of the 32 MiB snapshot budget. The unadvertised, development-only requests `virgil-lsp/analyze` and `virgil-lsp/snapshot` submit analysis and inspect retained server-owned results. [Development stdio requests](../development.md#development-stdio-requests) owns their triggers, unstable formats, input capture, concurrency, failure, and lifecycle behavior.

[Configuration](../configuration.md) owns the project integration status and remaining M3 work. Interactive [protocol transcripts](../../test/protocol/worker.py) exercise a compiler crash, a hang with concurrent replies and fragmented stdin, 20 Aeneas analyses across replacements, retained snapshot reads, lifecycle cleanup, and a worker that never handshakes. Both platform CI jobs run these tests.

### Measurements

Initial worker-heap measurements, before the later occurrence and display-data extensions: Linux x86-64, Intel Core i7-14700KF, `virgil-lsp analyze --stats --bindings --repeat=10` on the Aeneas sources and their dependencies (198 files, 80,285 lines, 2.9 MB). The server's heap was the default 200 MB in every row; only the worker's heap varied. Each analysis collected 162,929 bindings, and the result frame was 2.0 MB. The parse and verify columns are for analysis 10. [Supported program size](#supported-program-size) records current result sizes, and [Call sites](../architecture.md#call-sites) records the later collection timings.

| Worker heap | Parse | Verify | Collect bindings (runs 1 / 2 / 10) | Wall time (10 runs) | Peak RSS |
| --- | ---: | ---: | --- | ---: | ---: |
| 200m | 23 ms | 140 ms | 253 / 249 / 247 ms | 7.09 s | 205 MB |
| 256m | 23 ms | 43 ms | 209 / 184 / 166 ms | 5.05 s | 247 MB |
| 384m | 23 ms | 45 ms | 32 / 28 / 21 ms | 3.54 s | 328 MB |
| 512m | 23 ms | 33 ms | 29 / 28 / 17 ms | 3.49 s | 329 MB |
| 768m | 23 ms | 44 ms | 32 / 29 / 21 ms | 3.56 s | 329 MB |

Run in process before the worker existed, the same analysis ran out of heap at 128 MB and 160 MB, so its peak live heap is between 80 and 100 MB. At 200 MB and 256 MB the collector dominates. From 384 MB up, more heap makes no measurable difference, and the resident memory a worker reaches still grows with its heap. 384 MB therefore leaves about twice the peak live heap of the largest Virgil program available. Other measurements:

- Over 300 analyses of the Aeneas sources in one worker, the live heap after each analysis stayed at 164,163 bytes, and the UID counter grew by 32,462 per analysis.
- Replacing the worker after every analysis of a two-file program cost about 0.6 ms per replacement (200 analyses: 0.14 s, against 0.02 s with one worker).

## Consequences

- A compiler trap, an endless loop, or a leak ends or slows only the worker. The supervisor reports it, keeps the last snapshot, and continues.
- Releases must preserve the [executable placement](../../README.md#building) (M7). The handshake rejects a pair from different builds.
- Each new host target needs a `src/os/<target>/HostOs.v3`.
- Every analysis copies its sources into the worker and its results back. [Supported program size](#supported-program-size) records the measured source and payload sizes.
- A worker's resident memory approaches 384 MB on programs the size of the Aeneas sources. A program needing more than about 190 MB of live heap, about twice the Aeneas sources, overflows the worker heap. Every such analysis is reported as a crash until `WORKER_HEAP` is raised.
- Compact result counts can expand beyond the [frame limit](#channel-and-framing) when decoded. `AnalysisWireReader` separately admits result allocations against a 16 MiB budget: each count reserves array and record costs before allocating. Diagnostic strings reserve 32 times their length plus 64 bytes, including headroom for JSON escaping and response buffers; index strings, the string table's entries, reserve their length plus 64 bytes for snapshot storage. Null strings reserve nothing. Diagnostic record charges include both byte offsets and the conservative JSON response allowance; [`AnalysisWire.decodeResult`](../../src/worker/AnalysisWire.v3) owns those charges. Declarations reserve 128 bytes per record, including the default source-type target and parent integers (their names and signatures are in the string table), string table entries 8, files 256, occurrences 20 (four range ints and a declaration index), use-site types 8 (an occurrence index and a string index), and builtin uses 20 (four range ints and a string index); each count also reserves 64 bytes for array headers. Signature text reserves its bytes, 4 for each string's offset, and 64 for its array; signatures reserve their encoded bytes, 4 each for their offsets, and 64 for their array; and a file's calls reserve their encoded bytes, which the snapshot keeps. Counts are also checked against the remaining payload at each record's minimum encoded size: one byte for a string or a signature text string, twelve for a declaration, eight for a file, five for an occurrence or a builtin use, two for a use-site type, and three for a signature or a call; a parameter or argument count, against one byte for each. An over-budget result is a distinct too-large outcome, not a malformed result; the supervisor replaces the worker conservatively as described in the [restart policy](#restart-policy) and preserves the old snapshot. The [development source budget](../development.md#development-stdio-requests) and [client message limits](../architecture.md#framing) leave space for JSON parsing, source and encoded request buffers, an incoming worker frame, old and new snapshots during replacement or a [rename's preflight](../architecture.md#rename), and the [document store](../architecture.md#document-store). The CLI uses the [request admission rule](#restart-policy).

### Supported program size

The supported envelope is determined by source/request size, decoded result size, worker heap, and analysis time, not a fixed file or line count. The Aeneas sources and dependencies (205 files, 3.0 MB of source) and Wizard's `wizeng` v3i sources (164 files, 1.3 MB) fit the result budget with occurrences. Measurements with protocol version 5, which added [display text](../architecture.md#display-text) ([#105](https://github.com/SaltedTan/virgil-language-server/issues/105)), with version 6, and with version 7 (below), against the unchanged 16,777,216-byte allocation budget. `analyze --stats --bindings` prints a result's charged allocation:

| Program | Files | Source | Bindings | Charged result allocation | Share of budget |
| --- | ---: | ---: | ---: | ---: | ---: |
| Aeneas sources and dependencies | 205 | 3.0 MB | 188,349 | 13,250,205 bytes | 79% |
| Wizard engine, `wizeng` v3i sources | 164 | 1.3 MB | 65,748 | 4,631,312 bytes | 28% |
| `vendor/virgil/lib/util/*.v3` | 31 | 0.2 MB | 6,933 | 750,611 bytes | 4% |

For the Aeneas sources, protocol version 5 adds 1,465,667 bytes to the 11,351,159 of version 4 (68%). Their result has 42,011 declarations, 4,161 more, since a declaration that nothing uses has a site; 41,965 declaration sites; 10,485 use-site types; 9,146 builtin uses; and a string table of 34,791 distinct strings, 809,430 bytes. Names cross once in the table, rather than once per declaration, which pays for most of the added declarations. Its payload grows from 2,544,967 to 3,550,981 bytes. `lib/util` had 584,522 bytes with version 4. A retained snapshot is charged its result allocation plus its paths and provenance; at version 5, that of the Aeneas sources was charged 12,863,116 bytes, 46,290 more than its allocation, as with version 4. Admission reserves a full result budget beside the snapshot it replaces, so a snapshot has half of the 32 MiB [snapshot budget](../architecture.md#analysis-snapshots-partly-present); the version 5 snapshot used 77% of that half. The Wizard sources were not measured again; their row is their protocol 3 measurement at `c7791a1`. `OccurrenceCoverage:aeneas_sources` requires the Aeneas sources' result allocation and retained snapshot charge each to stay within 80% of the 16 MiB result budget.

The Aeneas and `lib/util` rows were measured again after layout references were indexed ([#111](https://github.com/SaltedTan/virgil-language-server/issues/111)), in the same way. That adds 42 uses to the Aeneas sources and 29 to `lib/util`, each the layout `L` in a `Ref<L>`, at 20 bytes of allocation each, and no declarations, sites, use-site types, or strings; the Aeneas payload grows by 434 bytes, to 3,551,347. Measured just before, at `89e21b8`, the two results were 12,816,314 and 733,085 bytes, 512 bytes below the protocol version 5 figures above, for 4 fewer declarations (42,007, with 41,961 sites). The retained snapshot charge grows by the same 840 bytes, and its share is unchanged. Protocol version 6, which indexes packings, changes neither program's result, since neither declares a packing.

Protocol version 7 adds [call sites](../architecture.md#call-sites) ([#126](https://github.com/SaltedTan/virgil-language-server/issues/126)), initially measured in the same way against `000c21f`. The Aeneas sources have 40,302 calls with 7,227 distinct signatures, and their result grows by 431,000 bytes, from 12,817,154 (76.4% of the budget) to 13,248,154 (79.0%): 231,599 for the calls, kept as their 218,479 encoded bytes, 5.4 a call, plus 64 for each file's count; 102,037 for 2,235 strings of signature text, 92,969 bytes, most of them parameter labels, since text that a declaration also has is a string table index; and 97,364 for the signatures, 68,328 encoded bytes and an offset each. Their payload grows from 3,551,349 to 3,934,096 bytes. At that measurement, their retained snapshot, as `OccurrenceCoverage:aeneas_sources` analyzes them, was charged 13,283,784 bytes, 79.2% of the result budget: the allocation, plus 35,630 for that test's paths and provenance. `lib/util` grows from 733,665 to 750,611 bytes. The test's 80% bound held at that measurement, with 137,988 bytes to spare. The snapshot keeps the calls and signatures in their encoding and makes objects per query: an object and an argument array for each call would be charged about 2 MB more, past the bound. The Wizard row was not measured again.

After call signatures stopped emitting generic parameter declarations even when their instantiated types are unchanged, the Aeneas result was measured again with the same pinned compiler sources (`7cf038fc13a5`), relative `vendor/virgil/` paths, and `analyze --stats --bindings`. The table includes this correction: charged allocation grew by 2,051 bytes from the initial protocol version 7 measurement, leaving 171,567 bytes below the 80% bound. Declaration signatures keep their generic parameters, so call labels can now require separate strings. The focused `OccurrenceCoverage:aeneas_sources` budget regression also passes. Excluding unbound `void(...)` and `Pointer.atField(...)` applications adds no per-call allocation, and the first such application in a program walks its syntax trees once, without allocating, to check that it declares nothing of either name. The Aeneas sources' result allocation is unchanged; `WORKER_HEAP` remains `384m`.

Collection, rather than the result, sets the worker's memory cost. The following heap and timing measurements predate the generic call-label correction above. Without calls, a fresh worker's analysis of the Aeneas sources allocates 197.0 MB, with no collection, of the 201.3 MB half of its 384 MB heap. The first version of call collection, with an object per call, added 7.5 MB, and the copying collection that this forced, of the live program, added 230 ms to the first analysis. Recording calls as bytes adds 3.6 MB, 2.0 MB of which renders their signatures, so that RESULT encoding ends at about 200.8 MB (200,761,976 to 200,791,536 bytes in fresh workers) and still does not collect, leaving about 0.5 MB of the 201,326,592-byte semispace before the forced post-analysis collection. Keeping nested calls' last-argument ends, so that a call does not read the calls nested in it again ([call sites](../architecture.md#call-sites)), adds 10 KB. A worker that has analyzed the program before starts with its retained heap, and collects during each analysis with or without calls; in such a worker, an analysis takes 400 ms against 374 ms without calls, medians of the 3rd to 12th analyses in one worker. Further growth in what a fresh worker allocates for the Aeneas sources will make its first analysis collect too, which costs about 200 ms. `WORKER_HEAP` would then need measuring again; see [Measurements](#measurements).

Protocol version 8 changes no ordinary analysis. Measured at the commit that adds it, with the same pinned compiler sources, relative `vendor/virgil/` paths, and `analyze --stats --bindings`, the Aeneas sources' charged result allocation is 13,250,205 bytes, as before, and a fresh worker's heap, read after encoding the result and before the forced collection in an instrumented copy of each build that differs only in its sources (3 runs of each), is 200,772,920 bytes before and after, with no collection, leaving 553,672 bytes of the semispace. That figure moves by a few bytes with the length of the build's revision string, which the handshake sends, so both builds used the same one. An ordinary request and its `ProgramAnalysis` carry no field for a scope query: a request with one is an `AnalysisScopedRequest`, and only its analysis (`AnalysisScopedProgram`) keeps the parsed program for the query. A completion's result holds only its candidates, at most 1,000 declarations and the strings they name, plus the builtin names hidden at the cursor.

Protocol version 9 changes no ordinary analysis either. The measurements used the same method, comparing `5dcbc37` with the commit that adds the member query, with the same `BuildInfo` revision string in both builds:

- The Aeneas sources' charged result allocation is 13,250,205 bytes before and after.
- A fresh worker's heap is 200,772,888 bytes before and after, with no collection, over 3 runs of each build.
- The normalized `RESULT` payloads are identical, at 3,936,036 bytes, and so are the `--bindings` and `--display` outputs.

A member completion's result holds only its candidates, at most 1,000, with their declarations, names, and details.

Keying the worker's per-source maps by ordered maps rather than `Strings.newMap` ([#139](https://github.com/SaltedTan/virgil-language-server/issues/139); see [Maps keyed by path or URI](../architecture.md#maps-keyed-by-path-or-uri)) changes no ordinary analysis either. - The normalized `RESULT` payloads are identical, at 3,936,035 bytes, and so are the `--bindings` outputs.

The parser fixes of [#155](https://github.com/SaltedTan/virgil-language-server/issues/155)'s items 4 and 5, for out-of-order position-index inserts and retrospective token coordinates, change no ordinary analysis's bytes. Measured as above against `ad890ee`, with the same `BuildInfo` revision string in both builds:

- The Aeneas sources' charged result allocation is 13,250,205 bytes before and after.
- A fresh worker's heap grows by 3,536 bytes, from 200,735,424 to 200,738,960, with no collection, over 3 runs of each build, leaving 587,632 bytes of the semispace. Each `AnalysisPositionIndex` holds one more field, for a buffer that these sources never allocate, 3,296 bytes in all, and the stack of retrospective token records, allocated once per program, takes 240.
- The normalized `RESULT` payloads are identical, and so are the `--bindings` and `--display` outputs.

Hashing the display's and the encoder's tables with a per-worker key, and ordering the types that share the compiler's type hash ([#155](https://github.com/SaltedTan/virgil-language-server/issues/155); see [Display text](../architecture.md#display-text)), changes no ordinary analysis's bytes either. The measurements used the same method, comparing `6d5de01` with that change, with the same `BuildInfo` revision string in both builds:

- The Aeneas sources' charged result allocation is 13,250,205 bytes before and after.
- A fresh worker's heap grows by 4,336 bytes, from 200,738,960 to 200,743,296, with no collection, over 3 runs of each build, leaving 583,296 bytes of the semispace. In these sources, 49 pairs of distinct types share a compiler hash, and so do the types of two calls of one callee; the display's type table and call keys keep each pair in a tree of two nodes (`AnalysisTypeKeyMap`), and the trees, their lists, and the two tables' added fields take those bytes. No pair's structural order is zero, so neither table allocates the list that it keeps for such keys, and the two tables' fields for it take 16 of the bytes. The string and declaration hashes add nothing to a table or its entries, and the worker reads its key, and fills the type hash's tables from it, into arrays that the program is built with: an array allocated as the worker starts added 24 bytes.

The commits after it change only the server, and [#165](https://github.com/SaltedTan/virgil-language-server/issues/165) only its scanner, so these figures stand for `3250aed`.

The [2026-10-25 protocol benchmark](../benchmarks.md#reference-baseline), at `ac815fab2c0396accb42b902841ec5e6b82aa0d1`, uses longer absolute source paths and measures the later declaration-hash caching and RESULT-buffer presizing changes against `6406edc`. An exact counting pass (`AnalysisResultSizer`) runs the same encoding code over a counter, then the writer is grown once to that count rounded up to eight bytes. Success and error results allocate one buffer and copy nothing. If the count differs from the bytes written, the worker logs a warning and still sends the result. Fresh Aeneas handling uses 192,269,264 bytes instead of 200,643,952, and live-after-GC bytes are 176,768 instead of 176,769, with identical normalized RESULT data and decoded allocation charges. Reused handling avoids its former collection and uses 196,228,248 bytes, leaving 5,098,344 bytes below the semispace capacity; different paths and worker history can still cross that boundary. These measurements supersede the historical headroom figures above for that benchmark workload; the limits and retirement policy are unchanged.

[#283](https://github.com/SaltedTan/virgil-language-server/issues/283) measured what that 196,228,248-byte figure was and why the margin narrowed. It was `worker.heap_after_handle_bytes`, the from-space used at the end of handling, not allocation alone: `worker.allocated_bytes` was 189,071,280, and the 7,156,968-byte difference was the 176,768-byte live heap, the 3,936,046-byte result, and about 3,044,154 bytes of request payload. The margin at the end of handling is what decides whether the next analysis collects, so the figure did not overstate it; the result grew by 366,753 bytes to 4,302,799, and allocation grew by 4,705,104 bytes, so on the current benchmark a reused Aeneas analysis ends at 201,299,696 bytes, or 201,303,984 at its maximum, only 22,608 bytes below the 201,326,592-byte semispace at that maximum. In an instrumented copy, `Semispace.fromSpaceUsed()` at the start of handling is 3,044,160 bytes for a fresh worker (3,043,734 of them the payload) and 7,523,312 for a reused one: the 176,768-byte live heap, the previous 4,302,799-byte result, and the 3,043,734-byte payload, within a few dozen bytes. A forced collection there leaves 3,220,464 bytes, so the previous result is unreachable garbage that the next analysis would otherwise carry.

The worker now drops the result after sending it and collects immediately, while the server decodes the result; the new collection is `force_gc_after_send_us`, reported against the next request. Collecting at the start of the next request instead costs 23.5 ms on a reused analysis when the server and the worker have separate cores (312.1 against 288.6 ms), because that collection always runs on the next analysis's critical path. The post-send collection takes 24,294 µs there but costs 0.9 ms end to end (289.5 against 288.6 ms), because the worker is otherwise idle until the next request arrives. On one shared CPU the post-send collection takes 39,416 µs and competes with the server's result decode, so a fresh analysis takes about 24 ms longer (356.4 against 331.7 ms) and a reused one is unchanged (293.6 against 294.4 ms, within noise), since the pre-send collection drops from 16,162 to 724 µs; collecting at the start of the request costs 9.6 ms on a reused analysis there (304.0 against 294.4 ms). Both placements leave a reused analysis at 196,996,848 bytes, or 197,001,136 at its maximum, 4,325,456 bytes below the semispace at that maximum, and a fresh analysis at 196,973,712 bytes, 4,352,880 below it, against 22,608 bytes before. These are six alternating blocks of 30 samples each, once with everything pinned to CPU 12 and once with the server on CPU 12 and the worker on CPU 14, as editors run them on different cores. A collection is not about a millisecond because a semispace collection also clears the to-space up to its high-water mark, the previous analysis's allocation; the post-send placement moves that clear off the analysis path rather than removing it.

An ordinary request still carries no query, and the call query's state lives only in a call request's analysis: the finder and the collector that `AnalysisScopedProgram.callAt` creates. A signature help's result holds only the call, its callee's declaration, and its signature.

Users can check total source bytes with `wc -c` over the files supplied to analysis (using current overlay contents for unsaved files). Source bytes alone must be below the [development stdio request's admission limit](../development.md#development-stdio-requests), which also includes paths and metadata. The CLI uses the [encoded-request admission rule](#restart-policy). Neither source limit guarantees a result will fit: declarations, occurrences, and especially diagnostics have different allocation charges. For a program that fits, `analyze --stats --bindings` reports its binding counts and the result allocation charged against the budget.

With similar binding, call, and diagnostic density, about **1.25 times the Aeneas sources** would exhaust the result budget, before the development request's source limit rejects about **1.4 times** that source set. These are sizing guides, not guaranteed capacities for arbitrary programs. If the decoded result exceeds its budget, reduce the files analyzed together to a smaller valid program/project; retrying the unchanged program or increasing `WORKER_HEAP` does not increase the server's result budget.

The remaining headroom is accepted for now. Adding occurrence kinds or display data must re-measure decoded result allocation and [binding collection time](../architecture.md#compiler-adapter). If it runs short, the snapshot could keep declarations in int arrays rather than an object each, as it keeps occurrences, at the cost of allocating a declaration for each query.

### Other limits

- The time limit uses `System.ticksMs()`, which reads the wall clock (`gettimeofday`). A clock change during an analysis can shorten or lengthen the limit.
- `analyze` no longer traps when the compiler does; [Running](../development.md#running) owns its failure output and exit behavior.

## Alternatives considered

- **Keep analysis in the server with adapter workarounds only.** This is the interim option from #12. It leaves the crash, hang, and UID paths.
- **One executable that starts itself as the worker.** This is simpler to ship, but the heap is fixed per executable. The server's resident memory would grow to the worker's 384 MB instead of staying within its own 200 MB.
- **`fork` without `execve`.** This avoids finding an executable, but the child has the server's heap size and a copy of its heap, including open documents. `execve` gives each worker a fresh compiler state and its own heap.
- **Threads.** Virgil has none, and a trap would end the whole process anyway.
- **JSON over the pipe.** The server already parses JSON, but its [value limit and per-value heap costs](../architecture.md#json-limitations-and-workarounds) make it unsuitable for worker results. The [supported program size](#supported-program-size) measurements show the binding counts that results must carry, each with a range and a declaration.
- **Keeping the program in a long-lived worker and answering queries there.** A crash or a replacement would lose the results with the worker. The policy above depends on the server owning its snapshot.
