# Aeneas parse and verify crash paths

This is finding 4 from the [compiler spike, PR #11](https://github.com/SaltedTan/virgil-language-server/pull/11), extended with the later parser-diagnostic and enum-set findings. Virgil has no exception handling, so a runtime trap (null dereference, failed cast, out-of-bounds index, stack overflow, heap overflow) kills the process just as `System.error` does. The original audit traced explicit failure calls and fuzzed `parse()` + `verify()` (target `null`) with 21.9k `test/**/*.v3` files and about 919k mutants; starred rows were reproduced with `build/virgil-lsp analyze`.

For rows 18–24, malformed-range parsing constructs a range with both bounds null at `Parser.v3:1102-1104`, `:1166`, or `:1170`; `parseExprStmt` dereferences it at `:933` (with `Vst.v3:906` in the resulting path). The adapter's expression-start recovery contains rows 18 and 19 but not rows 20–23. Row 24's CRLF prefix exhausts the error limit at `ParserState.v3:160` in `parseFile`; the outline normalizes CRs, so the prefix does not exhaust the limit and recovery returns `[]`. No vendor containment is implemented here.

The original investigation's negative findings remain: `ErrorGen.fatalReport` has no callers; `ErrorGen.fail`/`fail1`/`unexpectedType` exit only with `CLOptions.FATAL`, which defaults to false (`CLOptions.v3:143`); `context.fail`/`SsaContext.fail` is unreachable from parse and verify; and the `V3.fail` calls in `Ir.v3`/`VstIr.v3` run only when there are no errors. `System.error` at `Parser.v3:56` checks the keyword table at startup. Enum and variant matches are checked for exhaustiveness, and other matches without a default do nothing.

The spike's architectural conclusion still applies: semantic verification cannot safely run inside the server process. See [ADR-0004](decisions/0004-analysis-worker-process.md) for whole-program failure containment and the [development command guide](development.md#running) for CLI failure output. Single-file parsing still runs in the server. All three entry points use the [shared parser](architecture.md#compiler-adapter), but only `documentSymbols` normalizes CRs before parsing:

| Entry point | Contained | Still kills the server |
| --- | --- | --- |
| `parseFile` | 12 (bounded token extraction), 18 and 19 (expression-start recovery) | 13 (deep nesting), 20–24 (malformed ranges the recovery does not reach) |
| `documentSymbols` | 12, 18, and 19, as for `parseFile`; 24's CRLF-prefix variant (CR normalization allows recovery) | 13 and 20–23 |
| `analyzeProgram` | 12, 18, and 19 through the shared parser; remaining rows by the worker process boundary | None; worker failures cause replacement |
