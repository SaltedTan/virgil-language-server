# Aeneas parse and verify crash paths

This is finding 4 from the [compiler spike, PR #11](https://github.com/SaltedTan/virgil-language-server/pull/11), extended with the later parser-diagnostic, enum-set, and expression-statement findings. Virgil has no exception handling, so a runtime trap (null dereference, failed cast, out-of-bounds index, stack overflow, heap overflow) kills the process just as `System.error` does. The original audit traced explicit failure calls and fuzzed `parse()` + `verify()` (target `null`) with 21.9k `test/**/*.v3` files and about 919k mutants; starred rows were reproduced with `build/virgil-lsp analyze`.

For rows 18–24, a term that fails to parse leaves the start of a range null: an expression-start error at `...` or `..+`, or a malformed number (`Parser.v3:1102-1104`). The range is then built without an end too (`:1166` or `:1170`), and `parseExprStmt` dereferences it at `:933` (with `Vst.v3:906` in the resulting path). The adapter's range recovery consumes the malformed operator at an expression start, as before. After that error or a malformed number, it also consumes each following range operator that no term follows, so no range is built with neither bound. A range with an end, such as `xs[0x ... 1]`, is left to the parser, which reports only the malformed start. Recovery also runs past the error limit at `ParserState.v3:160`, which row 24's CRLF prefix exhausts in `parseFile`. No vendor code is modified.

The original investigation's negative findings remain: `ErrorGen.fatalReport` has no callers; `ErrorGen.fail`/`fail1`/`unexpectedType` exit only with `CLOptions.FATAL`, which defaults to false (`CLOptions.v3:143`); `context.fail`/`SsaContext.fail` is unreachable from parse and verify; and the `V3.fail` calls in `Ir.v3`/`VstIr.v3` run only when there are no errors. `System.error` at `Parser.v3:56` checks the keyword table at startup. Enum and variant matches are checked for exhaustiveness, and other matches without a default do nothing.

The spike's architectural conclusion still applies: semantic verification cannot safely run inside the server process. See [ADR-0004](decisions/0004-analysis-worker-process.md) for whole-program failure containment and the [development command guide](development.md#running) for CLI failure output.

Single-file parsing still runs in the server, as ADR-0004 decided. [Issue #61](https://github.com/SaltedTan/virgil-language-server/issues/61) chose guards in the adapter's parser driver for rows 13 and 18–24 instead of moving parsing out of process, which would add latency to every edit and need a fallback while no worker is available; [issue #70](https://github.com/SaltedTan/virgil-language-server/issues/70) added one for row 25. The guards cost about 4%: `virgil-lsp parse` on the eight largest Aeneas sources (648 KB) takes about 122 ms with them and 117 ms without (best of 15, Intel Core i7-14700KF). All three entry points share `AnalysisSingleFileParser`, its recovery, its stack limit, and its chain limit. Parser recursion may use up to 1 MB of the 2 MB stack, measured from where parsing starts, or less if needed to keep a 64 KB reserve above the runtime's red zone. At the next token skip beyond that limit, the parser reports `nesting too deep; parsing stopped here` if the error limit permits and continues as if the input ended there, dropping later errors. The nesting depth at that cutoff depends on the input, compiled frame sizes, and available stack.

The chain limit bounds the `range()` recursion that `parseExprStmt` starts on each expression statement. Each level of that recursion has its own operator, `.`, `(`, or `[` token, so the skip observer counts those tokens, other than the parentheses after `if`, `for`, `while`, and `match`. It counts per bracket level and adds a cached enclosing count to counts inside parentheses and square brackets, so an abandoned list cannot hide a chain and each depth check takes constant time. A comma in parentheses or square brackets without `...` or `..+` resets that level's count, keeping long tuples, argument lists, indices, and array literals unrestricted; commas inside type arguments do not reset it. The tracker distinguishes type delimiters consumed separately by the parser from comparison and shift operators consumed as tokens, so `<`, `<=`, and `<<` in list elements do not suppress resets. Closing a level discards its count, except that a square bracket holding a range operator adds its count to the enclosing level. An adjacent `[]` counts once without opening a level, including the atomically consumed `.[]` and `.[]=` member operators; an observed adjacent `]` is ignored. A `;` or `}` first abandons every parenthesis and square bracket inside the innermost block. A `;` then ends the count, as does a `}` unless an operator or suffix follows it. Before the parser reads the token that takes a count past 6,000, it reports `expression too long; parsing stopped here` and stops as for the stack limit. Local initializers and `return` expressions are counted alike, although their statements do not take the expression's range.

The threshold charges 128 bytes of stack to each counted token, so 6,000 tokens take 768,000 of the roughly 970,000 bytes that `virgil-lsp parse` has left above the parser's limit and reserve. If less is left, the threshold is lowered to fit. A level of `range()` recursion measured at most 73 bytes: `virgil-lsp parse` overflowed at about 28,984 binary operators (72 bytes each), 43,412 member suffixes (48 bytes), and 52,109 index or call suffixes (40 bytes). Ordinary code stays far below the threshold. The highest count in the 22,579 `.v3` files under `vendor/virgil`, `src`, and `test` is 256, from an enum with 256 cases that take arguments. A single enum with more than 6,000 such cases would stop too.
