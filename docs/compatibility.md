The scheduled `virgil-master` workflow builds and tests against current upstream `master` as an advisory signal. A failure there does not block merges. Away from the pin, the workflow skips the tolerance inventory check and the separately run cursor tolerance histories suite skips its pin-dependent checks because both inventories are generated from pinned Virgil sources ([inventory checks](benchmarks.md#release-scorecard)).

Each release supports exactly one Virgil revision, the one in this table. To find the revision of a server you have:

- run `virgil-lsp --version`, which prints it as `virgil revision: <full SHA>`;
- read its release's `manifest.json`, in the archive or as the `virgil-lsp-<version>-<target>.manifest.json` asset, where `virgilRevision` and `library.revision` give it, or the release notes' *Revisions* section;
- or read `virgil/REVISION` beside the executables, which the server checks against its own revision before it uses that library.

## Support policy

[ADR-0014](decisions/0014-compatibility-and-support-policy.md) records this policy and why. The [project file's stability contract](configuration.md#stability-and-evolution) covers `.virgil-lsp.json` itself, and this section doesn't change it.

### What a release supports

| Layer | Supported | Otherwise |
| --- | --- | --- |
| The compiler sources compiled into `virgil-lsp` and `virgil-lsp-worker` | The release's [pinned revision](#virgil-revision), fixed when it was built | Nothing at run time changes it. Upstream `master` is only an advisory CI signal. |
| The Virgil source you analyze, and `compilerArgs` | Analysis of source that the pinned compiler accepts, with its `-lang:` options ([Compiler flags](configuration.md#compiler-flags)) and the project's target, within the documented limits. A version 2 project file can name a supported target, and its project is analyzed as the pinned compiler builds it for that target. A project without a target is analyzed without one, as `v3c` does for its interpreter, so code written for a native target, which uses machine-level types such as `Pointer`, reports unresolved types there ([Target](configuration.md#target)). A program must also stay within the capacity limits ([supported program size](known-limitations.md#supported-program-size)). | Source written for another Virgil revision is analyzed as the pinned compiler sees it, best effort. Keep a release whose pin accepts it. |
| The library that `virgilDependencies` reads | The bundled `virgil/` library, which the server uses only when its `REVISION` matches the pin, or a client root at the pinned revision | A client root at another revision is best effort: the server doesn't check its revision, and doesn't reject it. |
| `virgil-lsp-worker` | The worker from the same build as the server | Unsupported. The server refuses a worker whose worker protocol version, server version, or source revision text differs from its own ([troubleshooting](troubleshooting.md#a-worker-missing-beside-the-server)). It doesn't compare the executables or their Virgil revision, so it doesn't detect every mismatch, such as two builds of one commit with different uncommitted changes; such a pair is still unsupported. |
| The VS Code extension | A platform VSIX with the server it bundles; with an external server, the versions in the [extension table](#editors) | Other pairs are untested. |
| Editors and hosts | The minimum versions in [Editors](#editors) and the platforms in [Host platforms](#host-platforms) | As those tables say, including best-effort WSL 2 and Intel macOS. |

A client root, `virgil.virgilRoot` or `VIRGIL_LOC`, only chooses the library files that a project's `virgilDependencies` reads and the runtime sources of its target ([The Virgil root](configuration.md#the-virgil-root)). It doesn't change the compiler compiled into the server, which still parses and type-checks everything at the pinned revision.

### Fixes and older releases

Routine fixes go into the next release of the current minor line only. There are no backports, no long-term-support line, and no second maintained compiler branch. Every published release stays on the [releases page](https://github.com/SaltedTan/virgil-language-server/releases) with its archives, VSIX files, manifests, and `SHA256SUMS`, so you can keep the release whose pin matches your code; it gets no further fixes. For a security or correctness problem, the maintainer may make an exception, such as a fix on an older line, without promising more.

### How changes are announced

`CHANGELOG.md` announces each of these, and its section for a release becomes the release notes:

- a new pinned Virgil revision, with the old and the new one;
- a language option that a new pin removes or changes, by name ([Language options follow the compiler pin](configuration.md#language-options-follow-the-compiler-pin));
- a higher minimum editor version, which may come in a minor release;
- a change to the public command line (`--stdio`, its `--max-message-bytes` option, `--version`, and `--help`), the documented initialization options, the client settings, or the advertised capabilities.

The project already adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html), as `CHANGELOG.md` says, and that needs a declared public API. ADR-0014 declares it: the server's public command line above and its documented initialization options, and the extension's client settings; the project file has its own [contract](configuration.md#stability-and-evolution). So, from 1.0, an intentional incompatible change to the command line or the initialization options needs a new server major version, and one to a client setting a new major version of the extension. Before 1.0, a prerelease may make one, and its notes say so. A change to the advertised capabilities is announced in `CHANGELOG.md`, but isn't part of the declared API.

### Outside the guarantee

These may change in any release without notice:

- the development commands, which `virgil-lsp --help` lists as unstable (`parse`, `analyze`, `repair`, and their options), and the worker policy options that `--stdio` also accepts;
- the [development stdio requests](development.md#development-stdio-requests);
- the protocol between the server and its worker. The server and worker of one build must still stay together;
- the wording of logs and messages.

## LSP baseline

The server targets a conservative subset of [LSP 3.17](https://microsoft.github.io/language-server-protocol/specifications/lsp/3.17/specification/). See [Lifecycle](architecture.md#lifecycle) for initialization behavior and [Document store](architecture.md#document-store) for synchronization capabilities.

Inlay hints use LSP 3.17 `textDocument/inlayHint` and optional `workspace/inlayHint/refresh` support. The server advertises no resolve provider and sends no insertion edits ([rules and settings](architecture.md#inlay-hints)).

The [repository setup script](../scripts/github-setup.sh) configures both pinned-Virgil CI checks, the `vscode-client` job, and `lazyvim-linux`, the [LazyVim test](../test/e2e/lazyvim/README.md#ci) on Linux, as required checks on `main`. On Linux, the pinned-Virgil check is the `test` job, which runs no tests itself: `test-linux-unit` runs the unit tests and the two `test-linux-suites` jobs each run a shard of the other suites, all at once, and `test` runs after them whatever their results. It passes only when all three passed, their reports show that the shards together ran every suite of `make test` exactly once, and every shard and the unit tests built the same executables, which it compares by SHA-256 digest (`test/suites.py --verify`, [Build and test](development.md#build-and-test)), so a failed, cancelled, or skipped shard fails the required check rather than passing as skipped. The macOS pinned-Virgil check, the `test-macos` job, confirms `test-macos-unit` and the two `test-macos-suites` jobs on Apple Silicon under Rosetta 2 in the same way. It runs on Linux, since it only reads their reports and digests, so a pull request runs at most four macOS jobs at once, under GitHub's limit of five for the account, and the required check never waits for a macOS runner. It does not include `vscode-extension-host`, `vscode-extension-host-macos`, or `lspcheck-linux`, the [protocol conformance check](development.md#protocol-conformance). Nor does it include the JVM build's jobs for Apple Silicon without Rosetta translation: `test-macos-jvm`, which builds the [JVM target](development.md#the-jvm-target) there and runs its tests, `jvm-package`, which packages its archive, VSIX, and runtime source archive on Linux and checks them, and `jvm-archive-macos`, which runs that archive's smoke tests, the VS Code client's tests, and the Extension Host test on that VSIX there. The Apple Silicon runners have Rosetta 2 installed. Each JVM job requires an arm64 machine and an untranslated runner process, reports Rosetta's presence and the status of `arch -x86_64 /usr/bin/true`, then rejects translation in every observed descendant and requires every Java process to run the expected arm64 `java`. Sampling can miss processes that end between samples. The maintainer decided on 2026-11-08 that these jobs start as advisory checks, which report failures without blocking a merge; they can be made required later, as `lazyvim-linux` was. The [nightly from-scratch workflow](../.github/workflows/nightly.yml) also runs daily on `main` and on `workflow_dispatch`: it rebuilds and tests from a fresh clone with no caches, with a randomized unit-test group order (`UNIT_SHUFFLE=1`), and on macOS runs `make test` against the newest Homebrew Neovim rather than the pinned 0.12.6 tarball `ci.yml` uses, so a Neovim regression surfaces before a PR reaches it. It is not a required check. See [Nightly from-scratch workflow](development.md#nightly-from-scratch-workflow). `jvm-package` runs in CI on every pull request. The two macOS jobs, which use most of a push's macOS runner time, are in the [JVM lanes workflow](../.github/workflows/jvm.yml) instead, by the maintainer's 2026-11-21 decision: it runs them after each push to `main`, nightly, by hand, and on a pull request only when the pull request changes `src/os/jvm/`, `test/jvm/`, `scripts/jvm-runtime.*`, `scripts/v3c.sh`, the `Makefile`, `jvm.yml`, or `package-jvm.yml`, and by hand on any branch with `gh workflow run jvm.yml --ref <branch>`, with its own `jvm-package` call for `jvm-archive-macos`. On `main` its runs never cancel each other but coalesce, so only the newest waiting run starts, and `jvm-archive-macos` waits for `test-macos-jvm`, so the lanes hold one macOS runner at a time. A failure on `main` opens an issue titled "JVM lanes failed on main", or comments on the open one, with the commit and the run. `lazyvim-linux` runs on every pull request, and its failure blocks the merge. It, `vscode-client`, and the Extension Host jobs restore the plugins, `node_modules`, and VS Code that they would otherwise download from caches that only `main` saves, keyed on every input that decides what a cache holds ([Build and test](development.md#build-and-test)); the weekly editor tests and the release workflow install them from scratch. It became a required check after it had passed 20 pull-request runs in a row, counting only each run's first attempt: a rerun, a skipped job, or a cancelled job earned no credit. An audit on 2026-11-01 found 103 such passes, on Neovim 0.11.6 and LazyVim 16.0.1, after the last failure, the first attempt of [run 40343723363](https://github.com/SaltedTan/virgil-language-server/actions/runs/40343723363/attempts/1), where installing the tree-sitter parsers failed before any editor check ran. `lazyvim-linux`, `lspcheck-linux`, and both legs of `vscode-extension-host`, the extension from source with a built server and the installed platform VSIX, each build the server themselves and run at the same time as the Linux test jobs, rather than waiting for them, and `vscode-extension-host-macos` does the same beside the macOS test jobs; the build is deterministic, though only `test` and `test-macos` compare digests across jobs. The weekly [editor tests workflow](../.github/workflows/editor-tests.yml) runs the LazyVim test on Linux with Neovim 0.11 and 0.12 and on macOS, the Extension Host test on macOS on an installed VSIX, both on macOS also with the JVM build on Apple Silicon without Rosetta translation, and the [Remote-SSH test](../clients/vscode/README.md#remote-ssh-test) on Linux, and none of its jobs are required. The [release workflow](releasing.md#how-the-workflow-works) runs the same jobs on each release's own archives and VSIX. Publishing requires the required editor jobs to pass, including the Remote-SSH test ([manual testing](manual-testing.md#vs-code)). The two advisory JVM editor jobs run independently of publishing during the JVM preview. Making any of these jobs required is a maintainer decision. Merging a change to the script does not apply it; a maintainer re-runs the script to update branch protection.

CI runs on every pull request, by hand, and for each push to `main`. The push trigger keeps the README's CI badge current. Because `main` requires pull requests to be up to date and merges squash them, a push usually carries exactly the tree that its pull request's CI passed on. A push-only check skips the build and test jobs only when a merged pull request associated with the pushed commit has the same tree at its head and a successful `pull_request` run of `ci.yml` on that head; the push run then reports success for that commit. Without that evidence, or if the check fails, the normal jobs remain eligible. Pull requests and manual runs skip the check and keep the normal jobs eligible too. Cancellation prevents guarded jobs from starting. Required check names are unchanged. Every job but that check and `jvm-package`, whose reusable workflow the release workflow shares, also checks its running time, which excludes queue wait, checkout, installs, cache restores, and uploads, against a budget in `scripts/ci-budgets.json`; `jvm-package`'s budget stays advisory, and only `scripts/check-ci-budgets.py summarize` reports on it. Budgets start advisory, warning without failing the job, and a maintainer can make one enforcing after 20 pull request runs in a row that passed on the first attempt within it; an enforcing budget fails its job, and with it any required check that confirms the job ([CI running-time budgets](development.md#ci-running-time-budgets)).

[ADR-0020](decisions/0020-jvm-fallback-for-apple-silicon.md) records the maintainer's 2026-11-03 decision: the Intel build under Rosetta 2 stays the default for Apple Silicon, and the JVM build ships as the preview fallback. [#191](https://github.com/SaltedTan/virgil-language-server/issues/191) set 2027-01-31 as the latest decision date and 2027-05-31 as the local-release target.

Switching the default is a later decision tied to Apple's Rosetta timeline. Only `darwin-arm64` has a JVM build; Linux x86-64 and Intel macOS stay native. Apple Silicon support will move to a native `arm64-darwin` build once Virgil supports that target. Until then, the default macOS assets need Rosetta 2, and the [JVM build](releasing.md#the-jvm-build-for-apple-silicon) is the option for a Mac without it: it needs neither Rosetta 2 nor a separately installed Java runtime. Install Rosetta 2 with:

```sh
softwareupdate --install-rosetta --agree-to-license
```

## Where the server runs

The language server runs on the machine that holds the files, which isn't always the machine showing the editor.

| Setup | `virgil-lsp` runs on | Install it on |
| --- | --- | --- |
| Editor on a Linux machine | That Linux machine | Linux |
| VS Code Remote-SSH, or Neovim over SSH | The remote Linux machine | The remote machine |
| VS Code Remote-WSL, or Neovim inside WSL | Inside WSL 2 | The WSL distribution |
| Editor on a Mac, local files | The Mac | macOS |

The [manual test matrix](manual-testing.md) records which of these setups were tried with each editor for each release. [Known limitations](known-limitations.md#platforms-and-editors) lists what the platforms and editors don't support.

The three earlier extension versions (`0.1.0`–`0.1.2`) have the same code, and differ only in their version numbers and READMEs; `0.1.3` adds the platform VSIX files that bundle the server, worker, and pinned Virgil library, the inlay-hint settings, and fixes for restarts during crash recovery, failed pipe writes, and lost framing. `0.1.4` uses `vscode-languageclient` 11.0.0, which sends every open document's `didOpen` as the client starts, before any request, so breadcrumbs survive a restart, drops a request that would follow `shutdown`, and adds the `virgil.semanticTokens` setting. `0.1.5` makes that setting's `auto` value follow the `titzer.virgil` extension while VS Code runs, restarting the language server when it changes whether the server sends semantic tokens. `0.1.6` says in its output channel that a bundled JVM build, such as the `darwin-arm64-jvm` VSIX's, needs no Rosetta 2 or Java installation. `0.1.7` adds `[virgil]` configuration defaults for formatting on explicit saves, tab indentation, and final line ends. `0.1.8` has the same code as `0.1.7`, and differs in its version number, its README, and the server that its platform VSIX files bundle. `0.1.9` updates `vscode-languageclient` from 11.0.0 to 11.0.1 ([#211](https://github.com/SaltedTan/virgil-language-server/issues/211)), keeping VS Code 1.91 as its minimum, and bundles `1.0.0-rc.1`. The extension relies only on standard LSP: full-text document synchronization, `publishDiagnostics`, `textDocument/documentSymbol`, `textDocument/definition`, `textDocument/hover`, `textDocument/references`, `textDocument/signatureHelp`, `workspace/symbol`, file events (`workspace/didChangeWatchedFiles`), and workspace-folder changes. With `0.1.0-alpha.2` and later, it also uses `textDocument/prepareRename` and `textDocument/rename` with versioned `documentChanges`, and `textDocument/completion`, whose `completionProvider` declares the trigger character `.` for [member completion](architecture.md#member-completion), none of which `0.1.0-alpha.1` answers. With `0.1.0-alpha.4` and later, it also uses `textDocument/documentHighlight` ([document highlights](architecture.md#document-highlights)), `textDocument/typeDefinition` ([resolved type navigation](architecture.md#type-definition)), `textDocument/implementation` ([implementation navigation](architecture.md#implementation)), and `textDocument/inlayHint` ([inlay hints](architecture.md#inlay-hints)), which `0.1.0-alpha.3` and earlier don't answer. With `0.1.0-alpha.5` and later servers, it also uses `textDocument/codeAction` ([the missing-semicolon quick fix](architecture.md#code-actions)), `textDocument/prepareTypeHierarchy`, `typeHierarchy/supertypes`, and `typeHierarchy/subtypes` ([type hierarchy](architecture.md#type-hierarchy)), and `textDocument/prepareCallHierarchy`, `callHierarchy/incomingCalls`, and `callHierarchy/outgoingCalls` ([call hierarchy](architecture.md#call-hierarchy)), which `0.1.0-alpha.4` and earlier don't answer. With `0.1.0-alpha.6` and later servers, it also uses `completionItem/resolve` for [completion item documentation](architecture.md#item-documentation). When the server advertises formatting, it also uses `textDocument/formatting` ([the formatting request](architecture.md#the-formatting-request)). It needs `virgil-lsp-worker` beside `virgil-lsp`, which its startup checks verify; a platform VSIX carries both.

With `0.1.0-alpha.5` and later servers, it also uses `textDocument/selectionRange` to expand selections through the current document's tokens, bracket groups, and declarations ([Selection ranges](architecture.md#selection-ranges)).

With `0.1.0-alpha.5` and later servers, it also uses `textDocument/semanticTokens/full` and, when its client supports it, `workspace/semanticTokens/refresh` ([Semantic tokens](architecture.md#semantic-tokens)). The extension's `virgil.semanticTokens` setting sends `initializationOptions.semanticTokens`, which servers without semantic tokens ignore.

With `0.1.0-alpha.5` and later servers, it also uses `textDocument/foldingRange` for syntax-based block and comment folds ([Folding ranges](architecture.md#folding-ranges)).

With extension `0.1.6` or later, VS Code uses `textDocument/formatting` for **Format Document** when the server advertises it. Development builds from `main` support the request, and `0.1.0-alpha.8` is the first release to support it. Extension `0.1.6` requires enabling `editor.formatOnSave` for formatting on explicit saves, and `0.1.7` and later enable it by default for Virgil files. Published server releases through `0.1.0-alpha.7` supply no formatting edits. With the defaults of `0.1.7` and later, VS Code's `files.insertFinalNewline` adds a missing final line end on save regardless of server version ([the formatting request](architecture.md#the-formatting-request)). VS Code and Neovim declare dynamic registration for it, so the server registers it for documents whose language is `virgil` only, and VS Code doesn't offer it for `.virgil-lsp.json`. Neovim's `vim.lsp.buf.format()` uses the same request. The Neovim and LazyVim tests check formatting ([Formatting in Neovim and LazyVim](../editors/nvim/README.md#formatting)). The Extension Host test checks VS Code formatting ([Formatting](../clients/vscode/README.md#formatting)).

With a server before `0.1.0-alpha.3`, every extension version needs a Virgil root. When neither `virgil.virgilRoot` nor `VIRGIL_LOC` gives an absolute path, `0.1.0-alpha.1` and `0.1.0-alpha.2` exit as they start, so VS Code has no language server, not even for single files ([#175](https://github.com/SaltedTan/virgil-language-server/issues/175)). Set `virgil.virgilRoot` to a Virgil checkout ([The Virgil root](releasing.md#the-virgil-root)), or install `0.1.0-alpha.3`, which starts without a root.

For `0.1.0-alpha.3`, it passed with `0.1.0` and with `0.1.1` on that release's server, with that release's test, no-root checks included. It also passed with `0.1.2` on the `0.1.0-alpha.2` and `0.1.0-alpha.1` servers, each time with the test of the server's own release, which always sets a Virgil root. `0.1.0-alpha.3`'s test, which also starts the server without a root, failed only there with `0.1.1` on the `0.1.0-alpha.2` server ([results](manual-testing.md#010-alpha3)).
