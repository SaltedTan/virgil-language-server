# Changelog

All notable changes to this project will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html). Server and VS Code extension versions are independent; see [docs/compatibility.md](docs/compatibility.md).

## [Unreleased]

### Fixed

- A completion that answers with only keywords, or with an empty list after `.`, now sets `isIncomplete` when the names are missing for a temporary reason, so that the client asks again as the user types: the analysis failed, did not start, or was replaced by a newer request. A keyword-only reply that typing more of the word can't change stays complete: in a comment, in a document with no project or worker, or where the project's analysis has no names at the cursor, as when another of its files doesn't parse ([#327](https://github.com/SaltedTan/virgil-language-server/issues/327)).

## [0.1.0-alpha.5] - 2026-10-28

### Added

- [Semantic tokens](docs/architecture.md#semantic-tokens) (`textDocument/semanticTokens/full`) color the names of classes, components, variants and their cases, enums and their cases, layouts, packings, methods, functions, fields, parameters, locals, and type parameters by the declarations that the project's analysis resolves them to, with the `declaration` modifier on a declaration's own name and `readonly` where the compiler says that nothing may assign it. Keywords, literals, comments, and operators keep the grammar's colors. The server asks supporting clients to refresh when an analysis changes the tokens of an open document that the client hasn't edited, as after a change to another file, and while a file can't be analyzed, clients keep the tokens they have. `initializationOptions.semanticTokens: false` turns them off. In VS Code, the `virgil.semanticTokens` setting defaults to `auto`, which turns them off while the `titzer.virgil` extension, which has semantic highlighting of its own, is enabled ([#313](https://github.com/SaltedTan/virgil-language-server/issues/313)).

- [Selection ranges](docs/architecture.md#selection-ranges) (`textDocument/selectionRange`) expand and shrink selections through tokens, bracket groups, declarations, and the current open document, including unsaved edits, without semantic analysis. Completed syntax before the first parse error remains available; VS Code and Neovim tests check exact chains ([#306](https://github.com/SaltedTan/virgil-language-server/issues/306)).

- [Folding ranges](docs/architecture.md#folding-ranges) (`textDocument/foldingRange`) fold brace blocks and multiline comments from the open document's current parser syntax, including unsaved edits, without semantic analysis. Replies honor client capabilities and keep only completed ranges before the first parse error; VS Code and Neovim tests check exact ranges ([#297](https://github.com/SaltedTan/virgil-language-server/issues/297)).
- A [missing-semicolon quick fix](docs/architecture.md#code-actions) inserts `;` before trailing whitespace or comments when reparsing proves that the current syntax error is gone. VS Code and Neovim can apply its versioned edit; only clients with literal code actions and `documentChanges` support receive it, and only fixes that end the line are preferred ([#299](https://github.com/SaltedTan/virgil-language-server/issues/299)).

- [Type hierarchy](docs/architecture.md#type-hierarchy) (`textDocument/prepareTypeHierarchy`, `typeHierarchy/supertypes`, and `typeHierarchy/subtypes`) shows a class's superclass, a variant case's variant, and the variant an open variant extends, and the classes, cases, and variants that extend a type, one level at a time, from the class hierarchy that verification records. VS Code shows it as **Show Type Hierarchy** and Neovim as `vim.lsp.buf.typehierarchy()`. An item from an earlier analysis still finds its declaration after edits in other files and after edits in its own file that leave the declaration where it was, and gets nothing once the declaration moves, is deleted, or is replaced, never a different declaration; VS Code and Neovim checks cover exact items ([#291](https://github.com/SaltedTan/virgil-language-server/issues/291)).
- An open file with a syntax error that [method-body fallback](docs/architecture.md#method-body-fallback) can't substitute, such as a file opened with the error already in it or one whose cached text was evicted, is now analyzed from its [current text with the damaged body emptied](docs/architecture.md#current-text-repair): every byte between the braces of the method or constructor body that holds the parser's first error becomes a space, except line breaks, so no offset or line moves and no syntax is guessed. If the text still fails to parse in another body, that body is emptied too, at most two. No string, byte literal, or block comment may be unterminated, and the file's braces must balance, or lack one `{` or one `}` as the next two entries describe. Definition, hover, references, type errors, and the other read-only answers outside the emptied bodies then work as they do with fallback, nothing inside them is answered, an emptied body that must return a value counts one error toward the 15-error limit, and rename is refused. Files opened with an expression that the next line continues, or with errors in two bodies, are analyzed too; an extra brace, a missing brace that neither brace rule places, an error in a header or a field initializer, and errors in three bodies stay unrepaired. In the [tolerance benchmark](docs/benchmarks.md#body-blanking-comparison), 118 of the 185 primary states keep definition, hover, references, and diagnostics on a cold open, as many as in warm sessions, and so do all 24 held-out states, with no wrong answers ([ADR-0009](docs/decisions/0009-current-text-repair.md), [ADR-0010](docs/decisions/0010-analyze-unrepairable-files.md), [#293](https://github.com/SaltedTan/virgil-language-server/issues/293), [#312](https://github.com/SaltedTan/virgil-language-server/issues/312)).
- An open file that lost one `{` is now [repaired](docs/architecture.md#current-text-repair) too when its indentation shows which brace is missing, instead of leaving the whole project without semantic answers. The method or constructor body that layout delimits is emptied, and no offset moves. Every other brace pair in the file must agree with the indentation, with tabs reaching the next multiple of 8 columns, the method's header must be on one line, and exactly one control statement's header in the method must have lost its `{` by layout; a method's own `{`, a header split over lines or with a comment before its parameters, and a method that could be a local function of an earlier method without a body stay unrepaired. The repair trusts indentation: when every brace pair of the intended file agrees with its indentation, it gives no wrong answer, but where the file's own indentation disagrees with its braces near the missing `{`, answers outside the emptied body can point at the wrong declaration ([known limitations](docs/known-limitations.md#no-error-tolerant-parsing)). In the [tolerance benchmark](docs/benchmarks.md#brace-rules-comparison), 180 of the 185 primary states keep definition, hover, references, and diagnostics, warm and cold, up from 118, and so do 15 of 42 new held-out states, with no wrong answers in any state, any of the 51 controls, or any session; across eight generated stress sets, no state whose intended file agrees with its indentation was read wrongly, and the only wrong readings, 720 of 13,536 block-holder states, have intended files that disagree ([ADR-0010](docs/decisions/0010-analyze-unrepairable-files.md), [#317](https://github.com/SaltedTan/virgil-language-server/issues/317)).
- An open file that lost one `}` is now [repaired](docs/architecture.md#current-text-repair) when every place where that `}` could have been leaves it in the same method or constructor, as when a match case's block or an `if`'s block in a lambda lost its `}`. The server parses the file with a `}` at each such place, up to the end of the line of the first syntax error, and empties the method's body only when every reading that parses agrees on it, before the body's own `}`; nothing is inserted, no offset moves, and indentation isn't read. A method's own lost `}` stays unrepaired, since the method could then end wherever its `}` could go, as do a lost `}` whose first error is in the outermost block that the file leaves open, a file with another syntax error, and one whose places would take more than 16 parses to read ([known limitations](docs/known-limitations.md#no-error-tolerant-parsing)). In the [tolerance benchmark](docs/benchmarks.md#brace-rule-3-comparison), 5 more held-out states keep definition, hover, references, and diagnostics, warm and cold, 2 of the 14 earlier ones that lost a `}` and 3 of 28 new ones, with no wrong answers in any state, any of the 56 controls, or any session; across nine generated stress sets, rule 3 accepts 10,285 of 119,705 files one `}` short and reads none wrongly ([ADR-0010](docs/decisions/0010-analyze-unrepairable-files.md), [#320](https://github.com/SaltedTan/virgil-language-server/issues/320)).
- [Call hierarchy](docs/architecture.md#call-hierarchy) (`textDocument/prepareCallHierarchy`, `callHierarchy/incomingCalls`, and `callHierarchy/outgoingCalls`) shows the methods, constructors, and field initializers that call a method or an explicit constructor, and the ones that it calls, one level at a time, from the direct calls that verification resolved. VS Code shows it as **Show Call Hierarchy** and Neovim as `vim.lsp.buf.incoming_calls()` and `vim.lsp.buf.outgoing_calls()`. A virtual call goes to the method of the receiver's static type, not to its overrides, and calls through function values and partial applications are left out ([known limitations](docs/known-limitations.md#call-hierarchy)). An item from an earlier analysis finds its declaration again as a type hierarchy item does, and gets nothing once the declaration moves, is deleted, or is replaced; VS Code and Neovim checks cover exact items and calls ([#298](https://github.com/SaltedTan/virgil-language-server/issues/298)).

### Changed

- The VS Code extension's version is now 0.1.4. It uses `vscode-languageclient` 11.0.0, which sends the `didOpen` of every open document as the client starts, before any request, so the active editor's breadcrumbs no longer go empty after a restart until the next edit; the library's other fixes in that release, to startup, shutdown, and connection-close races, are listed in its [release notes](https://github.com/microsoft/vscode-languageserver-node/blob/release/client/11.0.0/README.md#3185-protocol-1000-json-rpc-1100-client-and-1100-server). A request still waiting for the client's pending `didOpen` notifications or full-text changes when a stop began, such as a restart or the window closing, is now dropped before it is written, as the library does for a request to a stopped client, so the feature gets no result and no error is shown. The new `virgil.semanticTokens` setting, which defaults to `auto`, turns [semantic tokens](docs/architecture.md#semantic-tokens) off while the `titzer.virgil` extension, which has semantic highlighting of its own, is enabled. It works with `0.1.0-alpha.5` and `main`, whose servers also answer semantic tokens, selection ranges, folding ranges, the missing-semicolon quick fix, type hierarchy, and call hierarchy; `0.1.0-alpha.4` and earlier work as before, without them; `0.1.0-alpha.2` and `0.1.0-alpha.1` need `virgil.virgilRoot` or `VIRGIL_LOC` to give an absolute path, since those servers exit without a root ([compatibility](docs/compatibility.md#editors)).
- [Rename](docs/architecture.md#rename) renames a method together with its override family, the methods that it overrides and every method that overrides one of them in subclasses and variant cases, with every use of any of them, from the class hierarchy that verification records. A method that only shares its name with others, such as `render` in unrelated classes, can now be renamed, and they keep their name, and a new name that another method has is accepted. The preflight now also checks that every method overrides the same method as before, and refuses a new name that would make a method start or stop overriding one; a family with a member in a dependency or under the Virgil root is refused ([prepare rename](docs/architecture.md#prepare-rename), [#286](https://github.com/SaltedTan/virgil-language-server/issues/286)).
- A reused analysis worker now collects the previous result immediately after sending it, while the server decodes the result on another core, so a program near the worker's heap limit no longer starts every reused Aeneas analysis within a few kilobytes of a collection and reusing a worker costs no more than before. Reused Aeneas handling ends 4.3 MB below the semispace instead of 22 KB; with both processes on one CPU the collection competes with the result decode, so a fresh analysis takes about 24 ms longer and a reused one is unchanged ([worker margin](docs/decisions/0004-analysis-worker-process.md#supported-program-size), [#283](https://github.com/SaltedTan/virgil-language-server/issues/283)).

### Fixed

- Pinned Virgil moved to [`57318d37`](https://github.com/titzer/virgil/commit/57318d37e9fcca8de6fda5f9cd82d669479f49ff). Inheritance cycles now report diagnostics and preserve semantic answers elsewhere in the project instead of hanging or crashing the analysis worker; implementation and type hierarchy keep the surviving superclass edges ([#311](https://github.com/SaltedTan/virgil-language-server/issues/311), [titzer/virgil#820](https://github.com/titzer/virgil/pull/820)).
- The VS Code extension no longer sends the server a request after `shutdown`. A request that was still waiting for the client's pending `didOpen` notifications or full-text changes when a stop began, such as a restart or the window closing, went out after `shutdown`, because `vscode-languageclient` checks that the client is running only before that wait. The extension now drops such a request before it is written, as the library does for a request to a stopped client, so the feature gets no result and no error is shown. The [Extension Host test](clients/vscode/README.md#extension-host-test)'s recovery and restart checks now leave VS Code's breadcrumbs, inlay hints, and lightbulb on ([#314](https://github.com/SaltedTan/virgil-language-server/issues/314), [#212](https://github.com/SaltedTan/virgil-language-server/issues/212)).
- After a restart, the VS Code extension no longer lets a request for a document reach the new server before that document's `didOpen`, which could leave the active editor's breadcrumbs empty until the next edit. `vscode-languageclient` 10.1.2 sent the `didOpen` of a document that wasn't visible only when a request or another document's `didOpen` sent the pending ones, one at a time, and a request for a visible document, such as the breadcrumbs' document symbols, didn't wait for its own `didOpen` behind them; the server answered that the document had no symbols, and VS Code kept that answer for the document's version. The extension now uses `vscode-languageclient` 11.0.0, which sends the `didOpen` of every open document as the client starts, before any request, and sends an edit made meanwhile before a later request. The [Extension Host test](clients/vscode/README.md#extension-host-test)'s pending-edit restart check now leaves breadcrumbs on and checks that the new server gets no request for the edited document before its `didOpen`. The extension still requires VS Code 1.91 or later; the library's other fixes in this release, to startup, shutdown, and connection-close races, are listed in its [release notes](https://github.com/microsoft/vscode-languageserver-node/blob/release/client/11.0.0/README.md#3185-protocol-1000-json-rpc-1100-client-and-1100-server) ([#318](https://github.com/SaltedTan/virgil-language-server/issues/318), [microsoft/vscode-languageserver-node#1868](https://github.com/microsoft/vscode-languageserver-node/issues/1868)).

## [0.1.0-alpha.4] - 2026-10-26

### Added

- A [troubleshooting guide](docs/troubleshooting.md), organized by symptom, explains the messages that show why the server didn't start or a file gets no diagnostics or navigation in VS Code, Neovim, and LazyVim, and how to fix each cause. A [privacy statement](PRIVACY.md) says what the server and the editor integrations read, write, and start: they write no files of their own, collect no telemetry, and make no network connections ([#275](https://github.com/SaltedTan/virgil-language-server/issues/275)).
- Platform-specific VS Code packages for Linux x64 and macOS bundle the tested server, worker, and pinned Virgil library. An explicit `virgil.server.path` overrides the bundle; the universal VSIX retains the external-server fallback. Apple Silicon uses the Intel server under Rosetta 2 ([installation](clients/vscode/README.md#installing-from-a-vsix), [#267](https://github.com/SaltedTan/virgil-language-server/issues/267)).
- [Inlay hints](docs/architecture.md#inlay-hints) show inferred local types and direct-call parameter names, with independent settings enabled by default and source links for named types. VS Code, Neovim, and LazyVim checks cover exact labels and UTF-16 positions ([#265](https://github.com/SaltedTan/virgil-language-server/issues/265)).
- [Go to Implementation](docs/architecture.md#implementation) lists the source classes that extend a class, directly or transitively, including a variant's cases, and the methods that override a method, from the compiler's class and override hierarchy. Library classes and generic bases count; other declarations have none. VS Code, Neovim, and LazyVim navigation is covered by editor tests ([#274](https://github.com/SaltedTan/virgil-language-server/issues/274)).

- [Go to Type Definition](docs/architecture.md#type-definition) follows compiler-resolved value and call-result types, including generics, type parameters, and the `Ref<L>` layout exception. Built-in, structural, and unresolved types have no location; VS Code, Neovim, and LazyVim navigation is covered by editor tests ([#258](https://github.com/SaltedTan/virgil-language-server/issues/258)).

- A [clean install test](docs/releasing.md#clean-install-test) follows the marked README commands for VS Code, plain Neovim, and LazyVim in a fresh Linux container, using each release or weekly run's archive and VSIX with producer-recorded checksums. It checks diagnostics, definition, and hover with the shipped library and an explicit root ([#250](https://github.com/SaltedTan/virgil-language-server/issues/250)).
- A weekly [benchmark comparison](docs/benchmarks.md#scheduled-comparison) on Linux and macOS reports interleaved build timings and GC counts, uploads the JSON, and warns about large changes without failing on timing. The macOS job also renders a reference-baseline table, and [benchmarks](docs/benchmarks.md#macos-reference-baseline) records the first one, from the hosted Apple Silicon runner under Rosetta 2 ([#251](https://github.com/SaltedTan/virgil-language-server/issues/251)).
- Document highlights (`textDocument/documentHighlight`) show a declaration and its uses in the current document, with the same lookup, freshness, and waiting rules as references. See [Document highlights](docs/architecture.md#document-highlights) ([#229](https://github.com/SaltedTan/virgil-language-server/issues/229)).
- Syntax errors contained inside an open method or constructor body can preserve definition, type definition, inlay hints, hover, references, document highlights, and type errors outside that body using bounded last-parseable text. References and highlights may be partial; rename stays unavailable. Cold starts, closed broken files, and edits that fail the containment rule keep their existing behavior ([Method-body fallback](docs/architecture.md#method-body-fallback), [#243](https://github.com/SaltedTan/virgil-language-server/issues/243)).
- A [syntax-error tolerance benchmark](docs/benchmarks.md#semantics-during-syntax-errors) replays 185 repair and editing states through the protocol in warm and cold modes, checks semantic answers against parseable-program oracles, and rejects stale answers with deletion, signature, and shadowing controls. It records availability, correctness, latency, worker replacements, and optional heap probes without changing server behavior ([#239](https://github.com/SaltedTan/virgil-language-server/issues/239)).
- Release archives now include Virgil's complete pinned `lib/`, license, revision, and file hashes. With no client root, the server discovers that library beside its resolved executable; client roots take precedence, and invalid overrides keep their errors ([The Virgil root](docs/configuration.md#the-virgil-root), [#228](https://github.com/SaltedTan/virgil-language-server/issues/228)).
- Reproducible [performance benchmarks](docs/benchmarks.md) for pinned small, util, and Aeneas projects, with checked semantic answers, raw process-block samples, and build/host metadata. `make bench` builds opt-in phase and allocation probes; `make test` runs a small protocol smoke case ([#190](https://github.com/SaltedTan/virgil-language-server/issues/190)).
- A VS Code Remote-SSH test, `npm run test:e2e:remote-ssh` in `clients/vscode`, on Linux. It runs the Extension Host test's suite, unchanged, in the remote extension host of a Remote-SSH window: official VS Code 1.142.0 and Microsoft's Remote-SSH extension 0.129.2026100915, at pinned versions and checksums, connect to an SSH server of the test's own on 127.0.0.1, the packaged VSIX is installed on that host with the VS Code Server's CLI, and the test checks where the suite runs, the installed extension, and that no language server is left running after each window closes. It keeps its state and processes apart from the user's, and tells infrastructure failures from test failures by its exit status. The weekly editor tests workflow runs it three times, not as a required check, and each release now needs it to pass instead of a manual Remote-SSH session. It doesn't cover closing the window during a server's recovery, from checklist step 17, or what VS Code shows. See the [Remote-SSH test](clients/vscode/README.md#remote-ssh-test) and [manual testing](docs/manual-testing.md#vs-code).
- The VS Code [Extension Host test](clients/vscode/README.md#extension-host-test) now automates [manual checklist](clients/vscode/README.md#manual-checklist) step 17. It kills the server and, during the client's automatic recovery, runs **Virgil: Restart Language Server**, changes `virgil.server.path`, or closes the window, each in a check of its own. A script set as `virgil.server.path` holds the recovery's start until the action has happened, so that each check lands in the recovery every time. The checks confirm that the action waits for the recovery, that the recovered server receives the already-open `bad.v3` in a `textDocument/didOpen` before `exit` (on either side of `shutdown`), then exits with status 0 after exactly one `shutdown` and one final `exit`, and that one server is left after a restart and none after the window closes. These are regression checks for the spurious `didOpen` errors during recovery ([#194](https://github.com/SaltedTan/virgil-language-server/issues/194)). The [Remote-SSH test](clients/vscode/README.md#remote-ssh-test) runs the restart and configuration checks too, but not the window close ([#185](https://github.com/SaltedTan/virgil-language-server/issues/185)).
- A coverage manifest for the editor tests, `test/e2e/coverage.json`, which gives each automated check a stable ID and maps the checks to the manual test matrix and the VS Code checklist, marking what no test covers, and version 1 of a JSON Lines format for the tests' results, `test/e2e/results-v1.schema.json`. The tests don't write results yet. `make test` checks that the two files are consistent, and `scripts/editor-results.py validate` checks that a stream of results follows them, including the client mode, VSIX, and editor that each run records against its suite, so that only a record of the `manual` suite has `clientMode: manual`, with the same verdict on any Python 3.9 or later, since it limits an integer to 20 digits itself ([validating a stream](test/e2e/RESULTS.md#validating-a-stream), [#218](https://github.com/SaltedTan/virgil-language-server/issues/218)). `scripts/editor-results.py render` generates a release's table of runs and its matrix from the valid streams that a selection file lists, each pinned by its SHA-256, and writes them between the release's markers in `docs/manual-testing.md`, changing nothing else, or with `--check`, prints a diff if they're out of date. It refuses an unlisted stream beside the selection or a symlink under its directory, though the directory itself may be a symlink or under one, such as macOS's `/tmp` ([#227](https://github.com/SaltedTan/virgil-language-server/issues/227)), and two attempts of the same suite, setup, lane, and editor version, rather than choose one, and names the expected failure in LazyVim as a known limitation, apart from its workaround profile ([rendering a release](test/e2e/RESULTS.md#rendering-a-release)). No release's results are generated yet. See [Editor test results](test/e2e/RESULTS.md).
- Editor result streams now record the facts that decide each alternative, so the validator rejects a run that plans the side its editor doesn't allow: a Neovim 0.11 stream can no longer plan the built-in `:lsp` command's checks, and a client that declared no `workspace.didChangeWatchedFiles.dynamicRegistration` can no longer plan file watching. Unavailable facts keep a run from passing ([result events](test/e2e/RESULTS.md#result-events), [#220](https://github.com/SaltedTan/virgil-language-server/issues/220)).
- The VS Code [Extension Host test](clients/vscode/README.md#extension-host-test) now checks that **Virgil: Restart Language Server**, run while an unsaved edit is still waiting to be sent, loses no text. It starts the server from a script that records what each server receives, and checks that the old server never got the edit, that the new server's `textDocument/didOpen` has the buffer's exact text and version, which its document symbols then show, and that a later edit reaches the new server. The [Remote-SSH test](clients/vscode/README.md#remote-ssh-test) runs the check too. Such a restart can log `Delivering pending changes failed: TypeError: this.task is not a function` in the output channel, a `vscode-languageclient` bug that loses nothing ([known limitations](docs/known-limitations.md#platforms-and-editors), [microsoft/vscode-languageserver-node#1916](https://github.com/microsoft/vscode-languageserver-node/issues/1916), [#193](https://github.com/SaltedTan/virgil-language-server/issues/193)).
- The VS Code [Extension Host test](clients/vscode/README.md#extension-host-test) takes `--logs DIR`, where it keeps the VS Code logs of a launch that fails, with Chromium's log of the renderer's console, before it removes its temporary directory. The CI and release jobs that run the test upload what it kept as an artifact, as evidence of why VS Code's window sometimes stops responding during the first launch ([#205](https://github.com/SaltedTan/virgil-language-server/issues/205)).
- The VS Code [Extension Host test](clients/vscode/README.md#extension-host-test) now retries the intermittent pre-activation unresponsive-window or gone-renderer failure once, keeping the failed attempt's logs in the CI and release artifacts even when the retry passes ([#205](https://github.com/SaltedTan/virgil-language-server/issues/205)).
- The VS Code [Remote-SSH test](clients/vscode/README.md#remote-ssh-test) now retries the intermittent unresponsive-window or gone-renderer failure once when its remote bootstrap never started, keeping both attempts' records and logs even when the retry passes ([#259](https://github.com/SaltedTan/virgil-language-server/issues/259)).
- Protocol tests now replay captured VS Code and Neovim initialization exchanges during `make test`, then check document symbols and a clean shutdown, so regressions in these real clients' request shapes fail the default suite ([capture and normalization instructions](test/protocol/README.md#capturing-a-new-clients-initialization-messages), [#231](https://github.com/SaltedTan/virgil-language-server/issues/231)).

### Changed

- The VS Code extension's version is now 0.1.3. Platform VSIX files for Linux x64 and macOS bundle the tested server, worker, and pinned Virgil library, and the universal VSIX still needs an external server; an empty `virgil.server.path` selects the bundle, or `virgil-lsp` on `PATH` when there is none, while an explicit path overrides both. New settings, `virgil.inlayHints.types` and `virgil.inlayHints.parameterNames`, control [inlay hints](docs/architecture.md#inlay-hints). The extension no longer shows spurious `didOpen` errors when a restart interrupts crash recovery (0.1.0 to 0.1.2), restarts a server whose pipe fails instead of leaving none, and fails pending requests promptly when malformed server output stops the client. It works with `0.1.0-alpha.4` and `main`, whose servers also answer document highlights, type definition, implementation, and inlay hints; `0.1.0-alpha.3` works as before, without them; and `0.1.0-alpha.2` and `0.1.0-alpha.1` need `virgil.virgilRoot` or `VIRGIL_LOC` to give an absolute path, since those servers exit without a root ([compatibility](docs/compatibility.md#editors)).
- Performance benchmarks now include cancelled completion typing bursts, measuring the last useful reply, semantic diagnostics after the burst, worker replacements, and startup cost. The paired experiment rejected immediate worker reclaim because it delayed diagnostics ([measurements](docs/benchmarks.md#reclaiming-obsolete-jobs), [#262](https://github.com/SaltedTan/virgil-language-server/issues/262)).
- Document highlights distinguish assigned uses (Write) from other uses (Read), with declaration names always Text. Compound assignments, increments, and decrements are Write; field receivers, array variables, and indexes remain Read. The LazyVim test checks navigation between highlights with `]]` and `[[` ([#249](https://github.com/SaltedTan/virgil-language-server/issues/249)).
- Large-project analysis uses less temporary memory for both successful and diagnostic-bearing results, without increasing retained analysis memory. Repeated successful analyses also avoid a garbage collection ([performance benchmarks](docs/benchmarks.md#reference-baseline), [#240](https://github.com/SaltedTan/virgil-language-server/issues/240)).
- Requests answered from an analysis, such as definition, hover, and references, are faster in large projects. Each checks that every source of the analysis is still current, and that check now compares the canonical URIs the analysis already records instead of normalizing each URI again. On Aeneas, definition takes about 0.2 ms instead of 1.7 ms, hover 0.2 ms instead of 1.6 ms, and references 0.8 ms instead of 2.3 ms. - Single-file parser diagnostics for unsaved document overlays, with corrected comment offsets. See [Parser diagnostics](docs/architecture.md#parser-diagnostics) for publication behavior and [Compiler adapter](docs/architecture.md#compiler-adapter) for parsing and recovery details.
- Hierarchical VST-derived document symbols for open, unsaved buffers. See [Document symbols](docs/architecture.md#document-symbols) for supported declarations, ranges, and failure behavior.
- Versioned full-text document synchronization (`didOpen`, `didChange`, `didSave`, `didClose`) with exactly matching `initialize` capabilities. Stale/out-of-order changes, duplicate opens, and unsupported incremental changes are ignored and logged to stderr. In-memory overlays override disk through an injected reader, and local Linux/macOS file URIs are normalized to canonical keys. See [Document store](docs/architecture.md#document-store) for version, save, and URI identity rules. Unit and golden transcript tests cover synchronization and rejection sequences.
- `PositionMap` under `src/documents/`: coordinate conversion for document text. See [Coordinates](docs/architecture.md#coordinates) for supported encodings, line endings, and out-of-range handling.
- LSP lifecycle and `$/cancelRequest` notification handling. See [Lifecycle](docs/architecture.md#lifecycle) for initialization, shutdown, cancellation, and exit behavior.
- Golden transcript tests under `test/protocol/`: recorded `--stdio` input bytes with the expected output bytes and exit status, covering the lifecycle, fragmented, consecutive, malformed, Unicode, and oversized messages, and cancellation. `make test` runs them.
- Pending-request table and response matching for server-initiated requests. See [Server requests](docs/architecture.md#server-requests) for the completion contract, logging, and current limitations.
- `--stdio` transport: reads framed messages from standard input, dispatches them, and writes framed output to standard output, handling partial writes. `--max-message-bytes=<n>` sets the payload limit within the [supported memory budget](docs/architecture.md#framing). Skipped messages are logged to stderr. A malformed header, a failed write, or input that ends inside a message exits with status 1.
- LSP base-protocol frame reader: `Content-Length` counted in bytes, input split at any point, optional `Content-Type` with a UTF-8 charset (semicolons inside quoted parameter values don't separate parameters), a configurable payload limit that skips longer messages, incremental payload buffering and release of oversized staging buffers, and a bounded header. See [framing limits and buffering guarantees](docs/architecture.md#framing). A header without a valid `Content-Length` stops the stream.
- JSON-RPC 2.0 message model under `src/protocol/`: distinct request, notification, response, and error-response shapes; integer and string IDs echoed in replies; `params` absent, object, array, or null. See the [dispatch contract](docs/architecture.md#json-rpc-messages) and [lifecycle](docs/architecture.md#lifecycle) for notification handling and request errors.
- JSON parsing and rendering on top of Virgil's `lib/file/json`, with fixes for string escapes, carriage returns, numbers that aren't 32-bit integers, deep nesting, messages with more values than the heap can hold, and invalid JSON output. See [JSON limits](docs/architecture.md#json-limitations-and-workarounds) for admission rules.
- Whole-program analysis in the Aeneas adapter: in-memory sources are parsed and verified as one program (no initialization or code generation). Syntax and semantic errors come back as `AnalysisDiagnostic`s, and a verified use can be followed to its declaration.
- Development command `analyze` (with `--bindings`, `--stats`, `--repeat=<n>`) and `scripts/bench-analysis.sh`.
- ADR-0003: supported platforms are Linux x86-64 and macOS on Apple Silicon (Rosetta 2 for now). WSL 2 was supported at first and is best effort since the ADR's 2026-10-20 amendment.
- macOS CI job on an Apple Silicon runner, and macOS in the weekly Virgil-master check.
- Repository foundation: Apache-2.0 license, roadmap, community documents, issue and pull-request templates, and CI.
- ADR-0001 (Virgil-native server) and ADR-0002 (pinned Virgil adapter boundary).
- Pinned Virgil submodule at `9945e430` and a `make`-based build that compiles against it.
- `virgil-lsp` executable with `--version`, `--help`, and a development `parse` command that reports Aeneas syntax diagnostics.
- Unit tests for the Aeneas adapter and command-line smoke tests.

### Changed

- WSL 2 on x86-64 Windows is best effort: the Linux build is expected to run there but isn't tested ([compatibility](docs/compatibility.md#host-platforms)).
- Analysis results carry exact UTF-8 byte offsets for every declaration and occurrence, and snapshots look up uses by byte offset. Result allocation charges are unchanged. See [Coordinates](docs/architecture.md#coordinates) and ADR-0004's [supported program size](docs/decisions/0004-analysis-worker-process.md#supported-program-size).
- Pinned Virgil moved from `9945e430` to [`7cf038fc`](https://github.com/titzer/virgil/commit/7cf038fc13a5474836bec8b14c7a3e796fd07fa5) (2026-10-08). The server and worker now include upstream's garbage-collector fix for forwarding pointers in 64-bit heaps above 4 GiB, where the macOS build's heap lives. The compiler front end is unchanged, so diagnostics, bindings, and document symbols are identical.
- The development `analyze` command now uses the analysis worker, with timeout and analysis-count tuning options; see [Running](docs/development.md#running) for options and failure output. `make` also builds `build/virgil-lsp-worker`; see [Building](README.md#building) for executable placement.
- Analysis adapter caches a lazy per-file binding index and binary-searches definition queries, reuses compiler configuration across analyses, and counts the global type cache only for requested statistics. The development `analyze --bindings` command reuses its report buffer without copying each file's output.

### Fixed

- Whole-program parsing is about ten times faster again, after exact diagnostic byte ranges had made it about 13 times slower. Semantic diagnostics for a program the size of the Aeneas sources now arrive about 220 ms after a save instead of about 830 ms, and the analysis worker's peak memory falls from 385 MiB to 336 MiB. Parser diagnostics and document symbols for large open files are also faster. See [Coordinates](docs/architecture.md#coordinates).
- Over-budget analysis results now report that the program is too large rather than blaming a malformed worker. See ADR-0004 for the [replacement policy](docs/decisions/0004-analysis-worker-process.md#restart-policy) and [supported program size and recovery guidance](docs/decisions/0004-analysis-worker-process.md#supported-program-size).
- Parser diagnostics and document symbols no longer kill the server on an expression statement that chains tens of thousands of operators or suffixes, such as `1 + 1 + … + 1;`. Whole-program parsing shares this guard. See [Aeneas crash paths](docs/aeneas-crash-paths.md) for the chain limit and recovery behavior.
- Parser diagnostics and document symbols now contain deep parser nesting and the remaining malformed-range traps. See [Aeneas crash paths](docs/aeneas-crash-paths.md) for the recovery behavior and containment limits.
- Document symbols no longer kill the server on expression-start `...` or `..+` (for example, while typing `xs[...]`); the outline now shares the parser driver and recovery used for parser diagnostics. See [Document symbols](docs/architecture.md#document-symbols).
- Whole-program diagnostics now retain exact UTF-8 byte ranges through the analysis worker, including tabs in block comments, trailing line-comment EOF errors, and multi-byte source text. Compiler display coordinates remain available for CLI reports.
- Whole-program analyses no longer leave verified programs rooted in Aeneas's global type cache or its superseded, statically allocated bucket arrays. Dropped snapshots return close to the pre-analysis live-heap baseline; a fresh-process regression covers repeated analyses and error paths. See [compiler constraints](docs/architecture.md#known-constraints-of-the-compiler-front-end).
- Occurrence collection reports uses only once in default match cases, lambda bodies (including nested lambdas and field initializers), and superclass arguments shared with constructors.
- Match-case names and enum parameter fields now resolve in the [occurrence index](docs/architecture.md#compiler-adapter).
- Bound aggregate open-document overlays and warn clients when admission is rejected. See [Document store](docs/architecture.md#document-store) for the supported capacity, recovery policy, and parsing headroom.
- Corrected binding queries that targeted compiler-synthesized declarations or treated inline exports as uses. See the [binding contract](docs/architecture.md#compiler-adapter).
- Occurrence collection no longer traps on a null type binding left by verification errors, including `E.set.all` on enums with more than 64 cases.
- `scripts/bench-analysis.sh` reports failed input sets, command exit statuses and stderr, rejects runs without timing samples, and cleans up temporary files on exit.
